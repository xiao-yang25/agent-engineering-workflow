# 项目体系接入与维护

## 用途与触发

本指南定义如何为具体项目建立、检查和持续维护规范体系，不保存各项目的业务事实，也不规定统一目录树。
共享工程政策以 [engineering.md](engineering.md) 为准；执行委派和证据交付沿用 [agent_selection.md](agent_selection.md)，不在项目中重复这些规则。

在以下情况按需使用：

- 首次接入项目，尚未确认其规范、上下文和验证入口是否足以支持当前目标。
- 用户明确要求为全新项目建立体系，或改造已有项目的规范与流程。
- 开发中发现缺失或失效的项目约束、文档、运行或验收入口，影响当前任务。

已接入且入口有效的项目直接复用现有知识，不在每次任务中重新全仓盘点。
日常开发只补当前任务所需缺口；只有用户明确要求整体改造时，才扩大为较完整的体系盘点与整理。
建立规范是已授权项目目标的必要支持时可继续执行；纯咨询或只读审查仅报告发现与方案，不顺手修改项目。
本指南不扩大文件、网络、数据或预算权限，不要求重复确认已获授权的步骤，也不要求自动启用或新建 Skill。

## 共用准备与来源

先识别项目根目录、任务范围、已有用户修改和适用团队规则，按相关范围检查：

| 需要知道的事实 | 优先寻找的入口 |
| --- | --- |
| 目标行为与约束 | 已接受需求、项目 AGENTS、README、接口契约、设计决定 |
| 当前结构与运行路径 | 相关代码、构建配置、部署约定、现有架构说明 |
| 如何检查正确性 | 测试说明、脚本、测试注册、CI 和必要目标环境 |
| 如何继续未完成工作 | 现有 Issue、计划、调查记录、内部文档与证据索引 |

按 [来源权威规则](engineering.md#intended-behavior-and-source-authority) 区分已接受契约、实现描述、观察证据和未知项。
现有代码、测试或历史报告不能自动变成正确契约；有冲突时先确认预期行为，不通过改写规范让实现看起来正确。
性能阈值、兼容范围、失败恢复语义和数据保留规则需要已接受的依据，不能为填满模板而编造。
无需检查无关目录、凭证或现场数据，也不因文档列出设备就连接它；必要入口不可达时记录缺口及其对当前任务的影响。

## 全新项目：随首个增量建立

1. 明确使用者、核心场景、目标与非目标、硬约束，以及第一个可交付结果和验收依据。
2. Root 决定必要的技术与结构取舍；Worker 整理资料、验证可行性并执行已确定的方案。未确定的关键决策显式保留。
3. 先打通一条完整可运行、可验证的路径，同步建立必要的依赖准备、构建、运行和检查入口；不要先堆积无法验证的基础设施。
4. 随已确定的事实形成最小项目 AGENTS、使用说明和验收说明；可复用同一文件的相关章节，不要求每类信息各建一个文件。
5. 后续增量按语义影响补充约束、检查和知识，未验证假设保持标识；首个增量的完成依据沿用共享工程规则。

初始规范可以很短。不预建完整文档树、Skill 集合、多 Agent 框架或没有实际用途的脚本包装层。
如果任务仅要求需求或设计方案，交付对应方案和待验证项，不声称已建立可运行工程。

## 已有项目：基线与最小补齐

先确认接入范围：日常任务中的局部补齐，或用户要求的项目体系改造。两者都保留用户修改与已有团队约定。

1. 定位现有规则、契约和知识入口，追踪目标涉及的真实路径；已有文件能承担职责时直接复用。
2. 核对相关验证基线，包括现有检查入口、依赖、测试清单及能取得的版本结果。区分已有失败、环境问题、未运行项和当前改动引入的问题。
3. 简述保留什么、补齐什么、重复内容应回到哪个权威位置，以及需要解决的关键未知项。已有授权足够时继续，无需把这一步变成固定审批。
4. 分步完成必要修改，按受影响行为和项目验收规则验证；保留有依据的项目更严格要求，不能为采用共享流程而削弱门槛。
5. 更新实际受影响的文档与任务记录，保留证据和缺口；需要整体治理但不属于当前任务的问题作为后续项。

不为了套模板搬目录、重写架构或复制共享指南。历史偶然行为不能直接升级为契约，也不能在未确认兼容影响时任意删除。
仓外内部文档、部署边界及资料保密约定继续有效；接入不要求将这些内容搬入代码仓库。

## 项目级 AGENTS 的职责

项目 AGENTS 应简短，提供项目差异、必要的长期约束和具体入口：

- 需求与产品契约、架构、测试验收、内部资料分别在哪里维护。
- 哪些业务真值、所有权、状态或兼容边界必须遵守，以及其完整定义的位置。
- 具体改动如何找到对应配置、命令与验收要求；已有详细映射时链接到它。
- 项目更严格的要求、操作边界和其他执行者需要知道的项目差异。

全局与共享指南已定义的委派、模型、风险、审查方法和完成状态，不复制到项目正文。
项目保留原则的具体落点，例如“改某配置需要同步哪些来源并运行哪个检查”，而不是再次解释通用测试原则。
详细文档的文件名不强制统一；已有入口有效时，通过简短的项目 AGENTS 导航衔接，避免两份规则正文。其他 CLI 的入口按实际加载机制转发到同一套规则，不假定任意文件名都能自动识别。

共享入口必须对实际执行者可达。个人目录路径不直接复制进团队仓库；跨机器、离线或其他 CLI 的规则传递按 [协作指南](agent_selection.md#最小任务说明与结果) 处理。
无法访问必要规则时说明限制，不假定 Codex 与 Worker 自动读取相同文件，也不声称已经加载。

## 文档与持续上下文

每个事实有一个明确的权威维护位置，其他文件只引用；位置可以是仓库文件或项目允许的内部系统，同一类信息可以按职责分布在不同文档。

| 信息 | 维护方式 |
| --- | --- |
| 产品与接口契约 | 复用已接受的需求、README 或接口文档，说明目标行为 |
| 当前架构 | 复用架构说明或 README，反映当前边界和重要路径 |
| 重要决定 | 仅按共享规则记录值得长期保留的决定，沿用已有设计文档或 ADR |
| 持续任务状态 | 复用一份任务记录，保留当前目标、已确认决定与证据、未决项、下一步 |
| 运行与现场证据 | 在允许的位置保存原始结果，提供可定位且关联版本的索引 |

记录的更新时机、输出控制、压缩与恢复核验统一见 [上下文管理与接续](engineering.md#context-management-and-resumption)。
Git 提交历史不代替未完成调查的假设、失败实验与下一步。短任务无需新建 progress 文件，长任务也不维护多份重叠记录。
内部资料通过允许保存的文档标识、版本或索引定位；不要把真实凭证、敏感现场数据或个人工作区路径写入公开或团队仓库。
内部位置尚未提供时，在本次允许的任务记录或交付中说明已知线索与缺口；不虚构链接、不声称内部文档已更新。只有缺口阻止当前必要工作时才请求补充。

## 测试与验收体系

沿用 [证据规则](engineering.md#evidence-and-confidence) 与 [独立审查规则](engineering.md#independent-review-policy)。项目负责把它们落实为可执行的映射，而不重新定义通用政策：

| 受影响范围 | 真实检查入口 | 必要环境 | 场景与预期判据 | 结果位置 |
| --- | --- | --- | --- | --- |
| 按本项目模块或契约填写 | 现有命令、测试目标或受控操作 | 必要的依赖、配置与平台 | 能判断正确与错误的结果 | 对应运行报告或内部记录 |

这是一种信息结构，不要求另建表格文件；已有测试文档和 CI 能表达这些关系时直接复用。
核对检查依赖与注册清单、路径和命令，并按当前目标实际执行必要检查。文件存在不等于能运行，测试注册不等于 CI 已执行，历史绿灯不等于最终版本已通过。
真实集成场景按需提供可重复的最小闭环：准备依赖和测试数据、启动并确认就绪、执行关键用户路径、观察输出及必要的数据库状态/日志/Trace、清理本次资源并验证可再次运行。复用现有入口，不要求每个项目都引入浏览器、数据库或统一包装脚本。
区分本机快速检查、目标平台验证和真实集成场景；前者不能替代后者独有的行为。环境不可用时报告影响，不删除必需验收项。
CI 可以在仓外维护，定位其入口和对应版本结果；不能因仓库内没有配置就断言没有 CI，也不能因有配置就声称执行成功。
证据交付与版本、环境、原始结果的关联按 [最小任务说明与结果](agent_selection.md#最小任务说明与结果) 执行，不另建复杂日志系统。

## 可选 Skill 能力导航

仅根据当前宿主暴露的名称和描述识别设计、实现、审查、交接或 SOP 能力；不假定使用者已安装任何个人 Skill。安装、可调用、显式启用和实际验证是不同状态。

遵循 [Skill 使用与冲突处理](../AGENTS.md#skill-使用)：用户显式请求后才读取或使用对应 Skill，除非更高优先级指令要求。创建或安装不自动授权启用配套 Skill、提交或发布。没有确认入口时不提供猜测命令；个人安装路径和适配记录留在本机配置中。

## 重复动作的沉淀与告知

### 触发判断

以实际重复发生、或同类失败再次出现作为触发条件，不按"出现过几次"机械创建 Skill。触发后按动作性质分流：原则与方法在文档里讲清楚；确定性动作交给脚本或 CI 执行，不依赖临场记忆；只有需要判断、且步骤稳定可复用的多步骤过程，才列为 Skill 候选。

### 复用与落位

优先复用已有入口，仅在能力不足时补充，不新建平行版本或为统一命令外观增加包装层；可利用已暴露的名称与描述识别候选；未被用户请求时不读取、调用或遵循 SKILL.md。落位沿用既有边界：通用治理写入 共享指南目录；项目专用资产放在该项目现有允许的位置；确实跨项目复用的资产才放个人共享位置。

Skill 正文定义适用条件、必要判断与步骤，并引用权威规范；适合机械执行的动作由脚本承载，参考材料按需载入，不复制整套文档、不写死项目路径。

### 交付告知

遇到有实质收益的候选时，在交付简述中给出"建议 / 暂不建议"、理由、适用范围与落位位置；没有实际候选时不逐任务重复空提示。候选不等于自动创建或安装的授权；用户明确要求沉淀后，按该授权一次完成，不再重复确认。

创建或更新后主动给出名称、路径、适用场景、显式调用示例、实际验证结果与已知限制。创建不等于已启用，能否被调用以宿主的发现结果为准。验证至少覆盖一个代表性场景与不适用边界，异常分支按实际风险取舍；未真正运行过不得声称已验证。流程变化后及时更新或停用过期入口。

## 持续维护与接入完成

开发中依据实际影响更新权威位置：行为或兼容变化更新契约；结构变化更新架构或必要决定；构建、配置、测试和环境变化更新对应入口及检查映射；持续工作更新同一份任务记录。
无语义影响的小改动不要求新增 Spec、ADR 或任务文档。发现重复规则时收敛到权威位置，不删除有依据的项目差异。
发现重复失败、反复纠偏或入口失效时，按 [工作流自迭代](workflow_evolution.md) 记录证据并作最小修正；周期审视、允许的自动修改与观察/撤回统一由该指南维护，不要求每个小任务做正式复盘。

接入是否完成按本次范围核对：依据和职责可定位，必要规则对执行者可达，相关运行/验证前提与检查结果已经核实，持续任务能找到记录，重要缺口及其下一步明确。
阻塞当前目标的缺口尚未解决时不能称接入完成；不阻塞当前范围的长期事项可以明确留待后续。
规范文件创建完毕不等于项目可运行；接入完成也不代表产品验收通过或已经发布。最终交付沿用 [共享完成条件](engineering.md#persistent-records-and-completion)，说明实际完成范围和证据限制。
