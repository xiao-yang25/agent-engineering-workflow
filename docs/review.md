# 工程审查

**简体中文** · [English](en/review.md) · [文档首页](../README.zh-CN.md#指南导航)

围绕契约和风险，报告可定位的问题与证据。

<a id="scope-and-depth"></a>

## 适用范围与深度

遵循 [engineering.md](engineering.md)，按风险审查用户指定的改动、设计、模块或仓库。改动审查从 diff 开始，追踪受影响调用者、依赖和可观察行为；需要时读取未改代码，但不自动扩成全仓审计。区分本次引入和既有问题。

设计审查评估契约、假设和所需验证，不要求尚不存在的代码提供运行证据。所有权、并发、信任/授权、持久数据、外部效果和兼容性需要对应深度；改动小、非结构、某种代码风格、AI 生成或存在抽象，都不能单独证明低风险或缺陷。

默认输出为按严重程度排序的发现、重要不确定性、已执行验证和适用结论。

<a id="establish-the-contract-and-reconstruct-affected-behavior"></a>

## 确立契约并重建受影响行为

按[来源规则](engineering.md#intended-behavior-and-source-authority)独立于补丁确立契约。检查验收基线是否覆盖受影响保证，哪些缺失结果阻断验收；没有基线时从契约和风险重建，不能用“测试通过”定义成功。

重建足以解释结果和不变项、组件与数据/控制流、外部效果、资源与生命周期、状态转换、线程/任务/回调/进程边界，以及初始化、运行、关闭和相关故障的系统信息。

区分观察和静态推断，标出假设与未知顺序。只列确属契约且影响改动的不变量，不能把某种所有权或恢复模型强加给所有系统。

<a id="audit-implementation-and-cross-module-flows"></a>

## 审计实现与跨模块流程

对照契约检查：

| 领域 | 核心问题 |
| --- | --- |
| 正确性 | 输入、输出、分支、前置条件和状态转换是否正确 |
| 所有权/生命周期 | 创建、借用、转移、销毁、部分初始化、关闭和重建是否安全 |
| 并发 | 顺序、共享状态、锁、回调、取消和任务生命周期是否协调 |
| 错误/资源 | 部分成功、重试、超时、回滚、清理及资源/外部状态是否正确 |
| 兼容/转换 | 调用者、版本、配置、schema、协议、升级、中断和恢复是否受支持 |
| 信任/数据 | 校验、身份、授权、隔离及输出、错误、日志、缓存、外部调用是否泄露 |
| 性能 | 关键路径是否增加有实质影响的复制、分配、阻塞或争用 |

追踪跨边界的信息丢失、清理责任转移、校验前状态修改和关闭后回调。偏离仓库模式只有产生具体后果才是发现，既有模式也可能有误。

审查重要修复时，确认原故障机制、被破坏的不变量、负责边界和因果路径是否消除。机制未知则转入 [debugging.md](debugging.md)，不要把变通称为根因修复。

<a id="check-external-semantics-where-correctness-depends-on-them"></a>

## 正确性依赖外部语义时进行核验

识别语言、库回调、取消/销毁、内存顺序、OS、协议、数据库或设备 API 的关键假设。微妙或不确定时，用适用于实际版本/配置的权威文档、依赖源码或聚焦实验核验。记录来源、版本和限制；无法核验时限定相关结论。

<a id="audit-the-tests-and-choose-independent-validation"></a>

## 审计测试并选择独立验证

把测试作为代码审查：它证明哪个契约，预期从何而来，能否拒绝有意义的错误实现。判定基准不能复制复杂实现或与被测代码共享未验证假设。

对重要行为做思维变异：移除清理、丢弃错误、跳过转换/同步或未完成即成功，测试是否失败？实际变异测试只在证据需要时隔离执行。

可复现修复需核对 [coding.md](coding.md) 的修复前后可比证据。测试改动需解释旧预期错误、已授权行为变化或仅测试准备变化；关注弱化断言、删除用例、重试、放宽范围/超时、跳过不稳定测试和移除真实行为的 mock。

从契约与风险选择能改变结论的边界、生命周期、故障、并发、分布式、兼容、信任隔离和数据转换场景；不要求无关修改覆盖所有类别。

<a id="use-runtime-evidence-for-runtime-claims"></a>

## 使用运行时证据支持运行时主张

运行时主张需运行时证据；内部 STOPPED 标志不能证明 OS 资源已释放或远端已观察结果。按具体问题选择最小构建、测试、集成、复现、生命周期/压力运行及资源观察。

按怀疑机制使用 sanitizer、竞态检测、性能分析、调试和跟踪。一次干净运行不能证明缺陷普遍不存在，插桩也可能改变时序。

报告实际运行项、结果及必要版本/环境。拟议测试不算执行；必要证据不可得时说明前提及其对结论的影响。

<a id="examine-complexity-without-inventing-findings"></a>

## 检查复杂度而不制造发现

检查层次是否承担职责，标志是否矛盾，回退是否掩盖缺陷，兼容分支是否服务真实场景，注释是否过度承诺。名称或模式本身不是发现；必须指出决定权重复、清理含混、依赖错误、不必要状态或性能影响等具体后果。

检查操作重复、迟到、部分发生或未发生时的结果。只要求契约承诺的安全完成、明确失败、回滚、清理或恢复。

<a id="classify-and-report-findings"></a>

## 对发现分类并报告

每项发现包含具体问题、触发条件、后果、最小位置和证据；必要时给修复方向和验证。不要只写“多加测试”或“改进架构”。

| 维度 | 取值 |
| --- | --- |
| 严重程度 | Critical / High / Medium / Low，按后果与现实发生可能性 |
| 类型 | 实现、架构、契约、测试/验证缺口、外部语义 |
| 置信程度 | Verified / Reasonably Supported / Uncertain，按共享定义 |
| 是否阻断 | 是/否，并按验收与项目规则说明理由 |

严重程度不是置信度。验证缺口可很严重；不确定担忧不能写成确认缺陷。无具体证据场景的推测列开放问题，不填充发现。静态推断的故障不能声称已观察到。

<a id="review-outcome-and-handoff"></a>

## 审查结论与交接

| 结论 | 含义 |
| --- | --- |
| APPROVE | 所审范围无剩余阻断发现或证据缺口 |
| APPROVE WITH NON-BLOCKING FOLLOW-UPS | 验收已满足，仍有具体非阻断项 |
| REQUEST CHANGES | 有证据支持的缺陷或未满足要求阻断验收 |
| INSUFFICIENT EVIDENCE | 缺少必要决定或验证，无法形成验收结论 |

结论只适用于所审版本和证据。就绪不等于迁移/发布已执行，建议也不合并或发布。设计审查和信息审计给适当就绪判断，不强套合并结论。

先按严重程度列发现，再写假设、重要缺口、实际验证和结论。没有发现时明确说明并列出限制。交接保留证据与不确定性：局部缺陷转编码，结构缺陷转设计，未知原因转调试，预期争议转契约澄清。范围评估完整后停止，不为制造发现搜索无关区域。
