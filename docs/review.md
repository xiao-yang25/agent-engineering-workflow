# AI Agent 工程审查指南

<a id="scope-and-depth"></a>

## 适用范围与深度

遵循 [engineering.md](engineering.md) 中的共享规则。按与风险相称的深度，审查用户请求的改动、设计、模块或仓库。目标是对正确性、受影响契约和证据缺口作出具体评估。

对于改动审查，从 diff 开始，追踪受影响的调用者、依赖和可观察行为。评估改动需要时，检查未改动代码；不要把每次审查都变成全仓审计。区分发现的问题是由本次改动引入，还是此前已存在。无关发现应单独列出，除非它们阻碍所请求的结果。

对于明确要求的仓库审计或大范围结构变更，重建相关系统并检查重要的跨模块流程。对于设计审查，评估拟议契约和假设，不要要求尚不存在的代码提供运行时证据；应明确它将需要哪些验证。

把下列各节作为以风险为导向的工作流。根据故障后果、影响范围、恢复和不确定性，检查作者的风险分类；不要把改动小或不涉及结构等同于低风险。小型审查可以合并步骤并省略无关检查。涉及所有权、并发、信任/授权边界、持久化数据、外部影响或兼容性的改动，需要对应的深入分析。不要仅凭代码风格、由 AI 生成，或存在抽象就推断有缺陷。

默认输出应简洁：按严重程度排列的发现、重要不确定性、已执行验证，以及适用时的审查结论。只有所请求的审计深度确有需要时，才使用扩展报告。

<a id="establish-the-contract-and-reconstruct-affected-behavior"></a>

## 确立契约并重建受影响行为

使用[共享来源规则](engineering.md#intended-behavior-and-source-authority)，独立于补丁确立已接受的契约。当文档、实现和测试彼此一致时，仍需检查其解释是否共同依赖一个缺乏依据的假设。

审计验收基线：它是否覆盖受影响的保证、变更是否合理，以及哪些缺失结果会阻断验收？如果此前没有记录基线，从契约和风险重建，并注明尚未解决的决策。不要仅凭测试通过来定义成功。

重建足够的系统信息，以解释：

- 改动必须建立什么结果，哪些内容必须保持不变。
- 参与组件、数据流/控制流和外部可观察影响。
- 资源所有权、生命周期依赖和状态转换。
- 受影响路径上的线程、任务、回调和进程边界。
- 初始化、正常运行、关闭和相关故障行为。

追踪重要的端到端路径，例如：

```text
API → 校验 → 状态变化 → 工作线程 → 存储/传输
    → 完成/错误 → 清理 → 外部观察
```

区分观察到的行为与静态推理预测的行为。标明假设和未知顺序，不要将它们当成测量事实。

只列出对改动有影响的不变量。例如：资源失效后工作线程不能再访问它；已确认接收的工作不能被悄悄丢失；清理责任有明确定义；转换遵循已接受的状态模型。验证每项拟议不变量确实属于契约，不要假设所有系统都使用同样的所有权或恢复模型。

<a id="audit-implementation-and-cross-module-flows"></a>

## 审计实现与跨模块流程

对照契约和不变量检查受影响路径：

| 领域 | 审查问题 |
|---|---|
| 正确性 | 对受支持输入，输出、分支、前置条件和状态转换是否正确？ |
| 所有权 | 谁创建、拥有、借用、转移和销毁资源？引用是否可能超出所需生命周期？ |
| 生命周期 | 部分初始化、重复使用、关闭、重启和重新创建时会发生什么？ |
| 并发 | 什么机制建立执行顺序？共享状态、锁、回调、取消和任务生命周期是否协调？ |
| 错误 | 错误传播到哪里？部分成功是否可能被报告为全部完成？重试、超时、回滚和清理语义是否有效？ |
| 资源 | 内存、线程、句柄、套接字、文件、注册项或外部状态是否可能泄漏或保持过期状态？ |
| 兼容性 | 受支持的调用者、版本、配置、数据模式（schema）和协议传输格式是否得到保留，或进行了有意的迁移？ |
| 信任与敏感数据 | 校验、身份、授权和隔离是否在适当边界得到执行？受保护数据是否会通过响应、错误、日志、缓存或外部调用泄露？ |
| 数据/协议转换 | 受支持的新旧状态和参与方能否共存，或按所需顺序升级？中断、重复、回滚或前向修复时会发生什么？ |
| 性能 | 受影响的关键路径是否增加了显著的复制、分配、阻塞、争用或其他已测量开销？ |

查找跨边界故障：错误转换时丢失信息、清理责任转移不明确、校验前改变状态，或关闭后回调仍在运行。各个局部函数看起来都可能合理，但组合后却违反契约。

与相关仓库模式比较。识别重复的清理、重试、序列化、配置或同步机制，但只有存在具体后果时，才把偏离既有模式报告为缺陷。已有模式本身也可能不合适。

对于重要缺陷修复，检查原始故障为何可能发生、哪个不变量被破坏、修复是否作用在应负责的边界，以及该因果路径是否仍可能发生。如果机制未知，建议按 [debugging.md](debugging.md) 进行必要调查；不要把变通方案称为已验证的根因修复。

<a id="check-external-semantics-where-correctness-depends-on-them"></a>

## 正确性依赖外部语义时进行核验

识别关于语言行为、库回调、取消、销毁、内存顺序、OS 资源、协议、数据库或设备 API 的重要假设。对微妙或不确定的假设，使用权威文档、依赖源码，或适用于已安装版本和配置的聚焦实验进行核验。

仓库注释和通过的测试不能建立所有上游保证。反过来，通用的当前文档页也未必描述正在使用的版本。记录相关来源/版本和任何重要限制。如果无法核验，应继续对依赖该假设的结论保留限定。

<a id="audit-the-tests-and-choose-independent-validation"></a>

## 审计测试并选择独立验证

把已有测试作为代码来审查。确定它们证明哪些已接受行为、预期结果来自哪里，以及能拒绝哪些有意义的错误实现。

薄弱的判定基准会复制复杂实现，或从同一份被测代码推导预期值。如果 `a + b` 这样的简单表达式来自独立定义的契约，它就可以是有效判定基准。仅有语法相似，不会让测试形成循环论证；问题在于是否共享未经验证的假设。

对于重要行为，进行思维变异检查：如果移除清理、丢弃错误、跳过转换、省略同步，或没有完成工作就返回成功，测试会失败吗？记录会影响结果的缺口。实际变异测试是可选的，应隔离、可逆，并以所需证据为依据。

对于可复现的修复，检查 [coding.md](coding.md) 中描述的修复前/后回归证据。确认未修复时的失败针对目标缺陷，修复后的运行采用可比场景。如果不能比较，评估所说明的原因和替代因果证据，而不是从一次测试通过推断其对回归的敏感性。

对于测试变更，确定是旧预期有误、获授权的行为变化取代了旧预期，还是重构仅改变了测试准备。查找被削弱的断言、删除的用例、重试、过宽范围、膨胀的超时、跳过的不稳定测试，以及移除了受影响行为的 mock。这些需要解释，而不是一概拒绝。

从契约和风险推导额外场景，而不是简单复制作者的测试：

| 风险 | 有用的场景 |
|---|---|
| 输入边界 | 空值、零值、极限值、重复、格式错误或不受支持的输入 |
| 生命周期 | 部分初始化、重复关闭、重新创建、关闭期间仍有活动工作 |
| 故障与恢复 | 依赖不可用、部分工作后的超时、资源耗尽、重启 |
| 并发与时序 | 同时操作、延迟回调、取消、执行顺序改变 |
| 分布式行为 | 丢失、延迟、重复、乱序、分区、对等方消失或重启 |
| 兼容性 | 受支持的新旧使用方、持久化数据、外部对等方 |
| 信任与隔离 | 允许和拒绝访问、适用时的跨用户/租户场景、经次级输出泄露受保护数据 |
| 数据转换 | 已有记录、新旧格式、中断或重复转换、受支持的恢复或前向修复 |

选择能改变审查结论的场景。不要要求无关的局部修改覆盖每个类别。

<a id="use-runtime-evidence-for-runtime-claims"></a>

## 使用运行时证据支持运行时主张

区分静态推理可支持的属性与需要执行才能验证的属性。调用清理或设置内部 STOPPED 标志，可能无法证明某项 OS 资源已消失，或远端观察者看到预期状态。

运行审查所需的最小范围检查：按需选择构建、聚焦测试、集成检查、复现用例或生命周期/压力运行。只有当进程、线程、描述符、套接字、注册项、内存、日志或时序能回答具体问题时，才检查它们。

根据怀疑的机制使用 sanitizer、竞态检测器、性能剖析器、调试器和系统跟踪。一次工具检查未发现问题，不能证明缺陷普遍不存在。插桩可能改变行为；解释时序敏感结果时要考虑这一点。

报告实际执行了什么、重要时的版本/环境，以及结果。拟议测试不是已执行测试。如果无法收集必要的运行时证据，说明缺失前提及其对建议的影响。相关证据已经充分后，避免不必要的重复测试。

<a id="examine-complexity-without-inventing-findings"></a>

## 检查复杂度而不制造发现

检查新增层次是在落实某项责任，还是仅仅转发调用；标志是否编码了相互矛盾的状态；回退是否隐藏内部缺陷；兼容分支是否服务于真实受支持场景；注释是否承诺了实现不具备的保证。

Manager、Factory、Service 或 Adapter 这样的抽象名称本身不是问题发现。必须有具体成本或故障：决定权重复、清理不明确、依赖方向错误、不必要状态，或受影响的性能约束。

对于失败处理，询问操作发生两次、迟到、部分发生或从不发生时会怎样。确定所需结果是安全完成、明确失败、回滚、清理还是恢复。不要强加系统从未承诺的恢复语义。

<a id="classify-and-report-findings"></a>

## 对发现分类并报告

一项发现应明确具体问题、触发条件、后果、位置和支持证据。当修复方向和有用验证并不显而易见时，应提出建议。避免“增加更多测试”或“改善架构”之类泛泛建议。

区分以下维度：

| 维度 | 取值与含义 |
|---|---|
| 严重程度 | Critical（严重）：数据丢失或大范围不可用等严重后果；High（高）：在现实条件下对正确性/可靠性有重大影响；Medium（中）：影响有限或触发条件更窄；Low（低）：轻微但具体的影响 |
| 类型 | 实现、架构、契约、测试/验证缺口或外部语义 |
| 置信程度 | Verified（已验证）、Reasonably Supported（有合理支持）或 Uncertain（不确定），使用共享证据定义 |
| 是否阻断 | 是或否，依据任务验收标准和项目审查规则说明理由 |

严重程度描述后果和发生可能性；不确定性描述证据。验证缺口也可能具有高严重程度，而不确定的担忧不能被表述成已确认缺陷。对于缺口，解释尚未验证的属性，以及该属性失败为何重要。缺少具体且有证据支持场景的推测性担忧，应保留为开放问题，而不是充入发现清单。

简洁的发现格式如下：

```text
[严重程度] 标题 — file:line
触发条件与预期行为；观察到或预测的失败及后果。
证据与置信程度；类型，以及是否阻断所请求的结果。
有用时，说明修复方向或缺失验证。
```

使用最小相关位置。对于复杂问题，包含复现序列或跨模块路径。如果故障来自静态推断，不要声称已经观察到它。

<a id="review-outcome-and-handoff"></a>

## 审查结论与交接

需要提出建议的实现审查，使用：

| 结论 | 含义 |
|---|---|
| APPROVE（批准） | 相关检查支持所请求的范围，且没有剩余的阻断性发现或证据缺口 |
| APPROVE WITH NON-BLOCKING FOLLOW-UPS（批准，保留非阻断后续事项） | 当前验收标准已满足；仍有具体后续事项 |
| REQUEST CHANGES（要求修改） | 证据支持存在会阻断验收的缺陷或未满足要求 |
| INSUFFICIENT EVIDENCE（证据不足） | 必要决策或验证不可获得，因此无法确立验收结论 |

批准仅适用于所审版本和证据；它不是“任何缺陷都不可能存在”的声明。将结果与验收基线，以及风险要求的审查强度对齐。范围涉及迁移/上线时，验证就绪状态，并将就绪与操作实际已执行区分开。建议本身不会合并或发布任何内容。对于设计审查或信息性审计，说明适当的就绪评估，而不是强行给出合并建议。

报告先列发现，按严重程度排序。然后说明假设、重要缺口和已执行验证。如果没有发现，明确说明，并指出剩余限制。大型审计还可能需要系统模型、不变量评估、测试审计和已核验的上游依赖；只有有用时才包含这些内容。

按共享指南将后续工作分流：局部缺陷转编码、结构缺陷转设计、未知原因转调试、有争议的预期转契约澄清。交接时保留证据和不确定性。当所请求范围已完成评估，且重要发现和缺口已明确时停止；不要仅为产出更多发现而继续搜索无关领域。
