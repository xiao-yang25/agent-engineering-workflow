# 解释产物制作指南

**简体中文** · [English](en/explanation_artifacts.md) · [文档首页](../README.zh-CN.md#指南导航)

用于解释工程机制、方案取舍或验证结果。需要制作文字、图解/图片、交互 HTML 或讲解视频时按需读取；通用表达与证据要求由 [engineering.md](engineering.md#expression-and-delivery) 维护。本指南提供方法与示例，不要求每次生成多种形式，也不证明任何制作工具已安装或可用。

## 先确定解释目标

先复用当前任务的受众、已有知识、需要理解或决定的问题、事实来源和验收。仅补缺失项；尚未明确时按[澄清原则](engineering.md#clarifying-the-task-with-the-user)帮助选择。把“看起来不错”转成可检查的目标，例如“能指出重试等待怎样增长，以及图中没有计入哪些耗时”。

| 理解需要 | 优先形式 | 选择依据 |
| --- | --- | --- |
| 一个结论、步骤或条件 | 清晰文字与数值例子 | 可以直接说明，制作成本低 |
| 比较选项 | 表格 | 同一维度便于比较 |
| 关系、数据流或空间位置 | 图解/图片 | 需要同时看见对象和关系 |
| 改变参数并观察后果 | 交互 HTML | 读者需要自己探索情景 |
| 连续变化或分步推导 | 讲解视频 | 时间顺序或运动能帮助理解 |

形式由理解需要决定。可先做一个小样，再据反馈扩展；用户明确要求某种形式时按要求制作，重要可行性缺口先说明。工具、安装、资料外发和 Skill 沿用已有授权，采用已有可用能力，不默设新的服务或依赖。

## 清晰文字与 ASD-STE100 原则

采用清楚的主体和动作，一句尽量表达一个主要意思，步骤保持明确顺序，同一对象使用一致术语。保留条件、否定、例外、单位和不确定性；必要专业词先定义，不以简化为由删掉重要机制。

| 含糊表达 | 更可操作的表达 |
| --- | --- |
| “必要时进行适当处理。” | “请求超时后记录失败；只有符合已接受重试规则的请求才重试。” |
| “The operation should be performed prior to proceeding.” | “Save the file before you continue.” |

改写不能添加原文没有的规则；第一行的超时与重试行为只有在项目契约已接受时才适用。核对改写前后事实、条件和指代，再从读者视角检查能否执行或理解。

ASD-STE100 是包含写作规则和受控词典的英文标准。本工作流借鉴清晰性原则，不声称一般改写或中文文本符合标准。若任务明确要求标准合规，取得适用版本并按其规则和词典核验，报告覆盖与缺口；不以一个提示词或自动检查器代替完整核验。

## 图解与图片

1. 先列对象、关系、方向和图要回答的问题。技术关系优先用可编辑的 Mermaid、SVG 或项目已有绘图工具；空间示意、照片或插画按需要选择相应形式，不用装饰图代替技术关系。
2. 先做最小图，确定箭头表示调用、数据、控制还是时间；混用时明确图例。关键文字、数字和公式由可核对内容提供，生成图片中的文字与关系逐项检查。
3. 渲染后查看实际尺寸下的标签、遮挡、方向、图例、单位与对比度。颜色以外也能区分重要类别，附简短文字说明；科学数据图使用实际数据和可复现绘图方法。
4. 保留可编辑源文件和最终图。注明示意、实测或推断，关联数据与版本；关键关系不能只依赖低分辨率图片。

例如解释“提交成功是否等于部署成功”，分别画出本地提交、远端接收、构建和部署状态，标明每一步的观察来源；只有实际发生并有证据的步骤才标为完成。

## 交互 HTML

1. 定义模型、参数、范围、单位、默认值和预期结果，说明简化及不适用情景。先核对计算，再设计控件；交互不能给未证实假设增加事实地位。
2. 使用已有网页能力。简单模型可用单页 HTML/CSS/JavaScript 与 SVG；输入有可见标签，数值有单位，提供重置。布局让控制项、当前结果与解释能够一起理解，重要状态不只用颜色表示。
3. 运行实际页面，操作关键控件，检查默认值、边界、无效输入、重置和结果联动；对重要计算用独立数值判据核对。检查键盘操作、阅读尺寸和相关浏览器错误。只读源码不能记为交互验收通过。
4. 交付可打开的页面与源文件，说明运行方式、依赖和未覆盖项；需要离线使用时实际断网检查，不能仅凭文件存在声称离线可用。

一个有界示例是指数退避的等待解释：第 k 次重试前等待 d × 2^(k−1)，共 n 次重试，无上限和抖动，则总等待为 d × (2^n−1)。令 d 可选 0.5–2 秒，n 可选整数 0–4；固定判据包括 n=0 时为 0，d=1、n=3 时为 7 秒。页面展示每次等待和累计等待，并说明不计请求执行时间、超时、上限与抖动。这是教学模型，不能证明真实服务的重试行为或是否适合重试。

## 定制讲解视频

先明确受众、需要理解的机制、所需时长与交付形式；时长不明但不阻碍制作时可给建议。参考 3Blue1Brown 的逐步推导方法时，重点是一个场景承担一个解释步骤、对象变化与旁白相互对应、观众有时间看清结论；数学动画可考虑已有可用的 Manim Community 或项目既有工具，不把特定视觉风格作为效果保证。

1. 从已核对的文字或模型形成讲解提纲，写明核心结论、成立条件与例子；先校正内容，再制作动画。
2. 列简短分镜：每段的画面、旁白/字幕、数值或公式、时长和转场。内容或形式尚不确定时先预览一个代表片段，避免整段制作后才发现解释偏差。
3. 按已确认分镜制作，用低成本预览检查运动、布局和节奏，再输出最终文件；配音和字幕按交付需要生成并核对。
4. 播放最终视频，检查完整讲解顺序、关键帧、转场、公式、旁白/字幕的一致性和可读性；有音轨时实际试听。渲染成功只证明生成文件，不能证明解释正确或观众已经理解。
5. 交付视频和可复用的脚本/源文件，按需要附文字摘要、来源与限制；记录实际工具版本和检查。无法渲染、播放或试听时说明缺口，不称为完整验收。

上述重试例子的分镜可以是：一次失败及模型边界 → 依次出现 1、2、4 秒等待 → 累计得到 7 秒 → 对比改变参数并重申不计入的耗时。公式和旁白使用相同符号、单位与结果，动画逐步显示累计过程；不暗示所有失败都应该重试。

## 制作与交付的证据

复用原任务记录，保存解释目标、来源/数据位置与版本、重要假设、源文件、最终产物及实际检查。文件生成、呈现正确、模型计算正确、实际系统行为验证和人的理解是不同结论，按实际证据报告；不新增固定问答、复述或发布审批。面向学习的任务可按需让使用者预测参数变化或解释关键机制，以反馈是否需要调整解释。

共享指南保存可复用方法；任务产物和个人材料留在原任务允许的位置，不因制作解释而复制进本公开仓库。稳定重复且已有遗漏证据的步骤按[沉淀规则](project_workflow.md#重复动作的沉淀与告知)评估，创建或启用 Skill 仍需显式请求。
