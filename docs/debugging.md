# 故障调试

**简体中文** · [English](en/debugging.md) · [文档首页](../README.zh-CN.md#指南导航)

<a id="scope-and-minimum-output"></a>

## 适用范围与最低输出要求

遵循 [engineering.md](engineering.md)。故障已存在但机制未知时使用本指南，建立可区分替代解释的证据链后再指导修复；让症状消失的补丁本身不能证明根因。调查深度随风险和不确定性变化，直接证据已足够时不增造假说或报告。

持续复用一份简洁记录：症状、环境、最佳复现、观察、假说、证据限制和下一实验。先明确下一决定所需证据，机制清楚后补全修复验收基线；变更所需证据须说明理由，且不得因失败或环境不可用降低门槛。

<a id="establish-the-symptom-and-preserve-evidence"></a>

## 确立症状并保留证据

先按[共享陈述与置信规则](engineering.md#evidence-and-confidence)分开预期、观察和解释，并记录已知触发、频率、环境和影响。重启、终止、重置或破坏故障状态的改动前，按故障保留关键状态：崩溃的核心转储／线程／调用栈／此前错误；挂起的所有线程、等待、锁／资源、进程树和 CPU；泄漏的实际资源计数与生命周期；网络／分布式故障的本地与对等方状态、协议事件、时间戳和版本；性能回归的可比指标、负载、剖析、分布和利用率。

事故可在原因明确前执行已授权缓解，但应尽可能先保留证据，标明缓解，验证即时效果并保留根因未决状态。服务恢复不证明根因解决。

<a id="build-and-compare-reproducers"></a>

## 构建并比较复现用例

记录能复现或区分故障的构建、依赖、配置、输入、硬件／OS、负载、拓扑、时序和启动／关闭顺序。逐步提高频率、移除无关组件、简化输入并控制疑似交错，同时验证仍是原故障机制。比较正常与失败用例；通过／失败边界可靠时再二分版本或缩减配置。

间歇性运行成功不能证明候选版本正常；定义判据并保留无结论结果。无法复现时使用保留轨迹、崩溃证据、依赖语义和静态因果推理，明确缺失运行证据并降低置信度；不得伪造复现或无限重复无结论运行。

<a id="construct-a-failure-model"></a>

## 构建故障模型

建模相关数据／控制流、状态转换、所有权、资源、线程／任务及外部系统。时序故障重建事件线，将每项标为观察、推断或未知；合并分布式观察时考虑时钟差异。

区分根因（允许机制发生的缺陷）、触发因素、放大因素和症状。多个缺陷可以共同致因；从症状反推被破坏的不变量和首个无效状态，最后一条错误不一定是最初缺陷。

<a id="form-and-distinguish-hypotheses"></a>

## 提出并区分假设

存在替代解释时保留少量合理假说，按与观察一致性、解释力、未支持前提和测试成本排序；优先级不等于置信度。为每项记录支持证据、反证／限制和下一项有区分力的检查。主动寻找削弱首选解释的证据；阴性结果只在其覆盖范围内有效。证据矛盾时明确否定或修正，不得重释每项结果来维护初始猜测。

<a id="run-purposeful-experiments"></a>

## 开展有明确目的的实验

实验记录问题、假说、干预、预测、观察和解释；优先选择在竞争解释下结果不同的检查，尽量只改变一个因果变量。必须同时改变多个变量时标为探索性，未经后续证据不归因于单项变化。

调试改动须区分观察性插桩、刻意改变时序／故障／配置的诊断性干预，以及仍待验证的候选修复。日志、断点、sanitizer、额外锁或 sleep 可能改变时序、布局、缓存和 I/O；症状消失只是线索。工具只回答明确问题，例如失败位置、已执行路径上的内存／竞态、瓶颈、系统阻塞、协议到达或受控故障后的状态。

破坏性实验只能在适当环境及任务授权内执行；干预须可逆、与生产改动分开，撤销时保留用户编辑。不能因 sleep、禁用缓存或变异压制症状就留入最终补丁。实验失去区分力时重审复现、观察和模型；机制未明时避免大范围重构或随机叠补丁。

<a id="apply-failure-specific-checks-when-relevant"></a>

## 按相关性进行故障专属检查

| 类别 | 重点 |
| --- | --- |
| 并发／状态机 | 重叠、共享状态、顺序、同步、取消、关闭、转换权、迟到／重复事件和非法状态 |
| 所有权／生命周期 | 创建、借用、缓存／异步引用、清理、依赖顺序、部分初始化、重复销毁 |
| 分布式／网络 | 本地、远端、缓存与最终状态；丢失、延迟、重复、乱序、分区、重启、版本和时钟 |
| 资源泄漏 | 多次生命周期中的实际资源；区分缓存／延迟清理与违反契约的未释放 |
| 性能回归 | 可比基线、负载、环境、分布、吞吐、利用率和测得瓶颈 |
| 崩溃／挂起 | 首个无效状态、前序错误、原发／继发关系；各参与方等待对象、可推进者及等待环 |

性能根因须用测量区分 CPU/GPU、内存带宽、分配、争用、I/O 和同步；代码看似昂贵不构成根因。挂起应尽可能在终止前捕获状态；加超时不解释循环等待。内部空指针不能证明底层资源释放。

<a id="root-cause-gate-and-investigation-outcomes"></a>

## 根因判定关口与调查结果

把解释作为修复依据前，按风险所需置信度确立：被违反的契约／不变量；允许无效状态的条件／缺陷；连接症状的事件序列；支持证据与重要替代解释；改动为何中断机制；复现等证据限制。按[共享置信规则](engineering.md#evidence-and-confidence)标注结论；仍不确定时继续调查或明确标为实验，不得声称根因修复完成。

- **根因充分确立：**证据足以支持下一行动；交接编码、设计、契约澄清或外部依赖工作。
- **调查受阻／证据不足：**具体观察、权限、环境或决定缺失；报告事实、缺口和下一有用实验，并继续仍可独立推进的工作。
- **修复已验证：**实现与所需回归／机制检查完成；再按共享指南审查并判断任务完成。

有用且已授权的调查仍可做时不得提前退出，也不得重复不能补足信息的同一实验。受阻不等于解决；任务要求修复时，根因交接不等于完成。交接包含症状／预期、复现或证据、因果序列、置信度与替代解释、不变量和修复方向；实现缺陷转 [coding.md](coding.md)，所有权或架构模型变化转 [design.md](design.md)。

<a id="validate-the-fix-and-neighboring-invariants"></a>

## 验证修复及相邻不变量

修复须同时具备与论断相称的**回归证据**（原故障场景在相关环境满足预期）和**机制证据**（改动在声明假设内阻断或正确处理已识别因果路径）。可复现缺陷按 [coding.md](coding.md#choose-evidence-that-tests-the-behavior) 做可比的修复前失败／修复后通过；无法可靠比较时说明限制和替代证据，并判断是否满足验收基线。

有限次数成功不能有力排除低频故障；改进复现、诱发相关交错或增强机制证据，并记录负载、次数和限制。能解决剩余不确定性且不影响用户工作时，可在隔离环境做 A/B/A；撤回修复仍须安全，之后移除诊断变异并验证最终版本。

审查 sleep、重试、超时、更大缓冲、忽略错误和默认值对应的故障类别、边界与残留状态；它们不能替代未知原因的解释。只在修复影响或仍有缺口时扩展到清理、同步、延迟、内存、兼容、错误传播、重试和恢复。最终报告修复、因果推理、针对最终版本的实际检查和剩余不确定性；需要时按 [review.md](review.md) 审查。只有验收满足才称修复已验证，否则区分已实现代码与缺失证据或阻塞项。
