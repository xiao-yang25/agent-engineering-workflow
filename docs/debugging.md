## 适用范围与最低输出要求

遵循 [engineering.md](engineering.md) 中的共享规则。当故障已经存在，但其因果机制尚未得到充分理解时，使用本指南，尤其适用于间歇性、并发、生命周期、分布式或性能问题。

建立有证据支持的解释，用它指导修复，并将修复与压制症状区分开。让故障消失的补丁是有用证据，但它本身不能说明系统为何失败。

调查深度应与不确定性和风险相称。确定性的局部缺陷可能只需要一个复现用例和简短的因果解释。复杂故障可能需要时间线、相互竞争的假设和多次实验。当直接证据已经建立相关机制时，不要编造额外假设或报告。

持续工作保留一份简洁记录：症状、环境、最佳复现用例、观察、假设、证据限制和下一项实验。复用这份记录进行进度更新和交接，而不是维护多份相互重叠的报告。使用共享风险评估判断故障的后果和影响范围，并明确下一项决策所需的证据。随着机制逐渐清楚，完善修复的验收基线；对所需证据的任何改变都要明确说明。

<a id="establish-the-symptom-and-preserve-evidence"></a>

## 确立症状并保留证据

在选择原因前，先描述预期行为和观察到的行为。已知时，包含触发条件、频率、环境和影响。使用共享的陈述类型与置信程度定义，将观察和解释分开。

例如：

```text
预期：销毁 Service 会移除其发现注册。
观察：100 次关闭中有 1 次，远端观察者在 5 秒后仍能看到它。
环境：release 构建，多线程生命周期测试。
假设：worker 关闭可能与 registry 清理发生重叠。
```

该观察不能确定原因是 工作线程 竞态、异步清理，还是观察者缓存。

在重启、终止、重置，或应用会破坏故障状态的改动前，保留有价值的故障状态。根据故障选择证据：

| 故障 | 有用的状态 |
| --- | --- |
| 崩溃 | 核心转储、出错线程和指令、调用栈、相关内存、此前的错误 |
| 挂起 | 所有线程的调用栈、等待状态、锁/资源所有权、进程树、CPU 使用率 |
| 资源泄漏 | 句柄、描述符、内存、线程、注册项或设备资源的数量和生命周期 |
| 网络/分布式故障 | 本地与对等方状态、协议事件、抓包、路由、时间戳、版本 |
| 性能回归 | 基线与回归后的指标、工作负载、性能剖析、延迟分布、资源利用率 |

如果正在发生的事故需要在原因查明前采取已获授权的缓解措施，应在可行时保留可用证据，并将该操作标为缓解措施。验证其即时效果，记录尚未解决的原因。服务恢复不能证明根因已解决。

<a id="build-and-compare-reproducers"></a>

## 构建并比较复现用例

通过记录构建、依赖版本、配置、输入、硬件/OS、负载、拓扑、时序以及相关启动/关闭顺序，逐步获得可控制的故障。只记录有助于复现或区分故障的维度。

逐步改进复现用例：提高发生频率、移除无关组件、简化输入，然后尽可能控制怀疑存在的交错执行。相比大量不受控的重复，同步屏障可能更可靠地暴露竞态。验证简化或放大操作保留了原有故障机制，而不是制造了另一个缺陷。

比较正常用例与失败用例。有用的差异包括修订版本、依赖版本、编译器标志、debug/release 构建、机器、配置、输入、负载和执行顺序。当通过/失败边界可靠时，使用回归二分定位，或逐步减少配置/组件。

间歇性故障的判定可能误导二分定位。明确如何判定候选版本，并保留无法得出结论的结果，而不是把每次运行成功都视为该修订版本已知正常。

无法复现时，使用保留的轨迹、崩溃证据、依赖语义和静态因果推理。说明缺少的运行时证据，并据此限制置信程度；不要伪造复现用例，也不要无限重复无结论的运行。

<a id="construct-a-failure-model"></a>

## 构建故障模型

对相关数据流/控制流、状态转换、所有权、资源、线程/任务和外部系统建模。对于时序敏感的故障，重建事件时间线，将事件标为已观察、推断或未知。合并分布式观察结果时，要考虑时钟差异。

例如：

```text
T0 已观察：关闭开始
T1 已观察：请求停止
T2 已观察：registry 销毁开始
T3 未知：  worker 访问 registry
T4 已观察：worker 退出
```

这条时间线指出一个可能发生无效访问的窗口，但不能证明 T3 确实发生过。

区分因果角色：

| 角色 | 含义 | 示例 |
| --- | --- | --- |
| 根因 | 使故障机制得以发生的缺陷 | 工作线程 生命周期未与 registry 生命周期协调 |
| 触发因素 | 激活一次故障的条件 | 工作线程 在关闭期间唤醒 |
| 放大因素 | 增加发生概率或影响 | 负载扩大了重叠窗口 |
| 症状 | 观察到的后果 | 无效访问、崩溃或过期的外部状态 |

可能存在多个共同促成故障的缺陷。不要强行把每次事故都解释成单一原因。从最终症状反向追踪被破坏的不变量：分配失败可能暴露错误路径中的缺陷，进而破坏状态，最终导致关闭时挂起。最后一条错误消息不一定指出最初的缺陷。

<a id="form-and-distinguish-hypotheses"></a>

## 提出并区分假设

只要其他解释仍然成立，就保留一小组合理解释。按其与观察的一致性、解释力、未经支持的假设和测试成本排序。优先级不等于置信程度。

当表格能让调查更易理解时，使用表格：

| 假设 | 支持证据 | 反驳证据或限制 | 下一项有区分力的检查 |
| --- | --- | --- | --- |
| 工作线程 访问无效的 registry 状态 | 清理开始后 工作线程 仍可能存活 | 尚未捕获无效访问；这是证据缺口 | 捕获访问顺序，或诱发怀疑存在的重叠 |
| 观察者返回过期的缓存状态 | 只有远端观察报告该注册项仍在 | 本地清理结果仍需验证 | 比较本地资源状态与一个新观察者的结果 |

寻找会削弱当前首选解释的证据。记录阴性结果及其覆盖范围：描述符数量稳定，会限制该工作负载下描述符泄漏假设的适用性，但不能排除所有资源泄漏。

如果证据与假设矛盾，明确否定或修正该假设。不要重新解释每个结果来保住最初的猜测。

<a id="run-purposeful-experiments"></a>

## 开展有明确目的的实验

对于有意义的实验，记录问题、被检验的假设、干预措施、预测结果、观察结果和解释。简单实验用几行即可。

优先选择那些在不同竞争解释下会产生不同结果的观察或干预。可行时只改变一个因果变量。如果必须改变多个变量，将结果标为探索性结果；没有后续证据时，避免把效果归因于其中一项变化。

对调试改动分类：

| 改动 | 目的 |
| --- | --- |
| 观察性插桩 | 在不刻意改变语义的情况下捕获状态，例如跟踪或计数器 |
| 诊断性干预 | 刻意改变时序、顺序、故障或配置，以检验假设 |
| 候选修复 | 实施一项拟议修正，其效果仍需验证 |

插桩可能改变时序、调度、分配、内存布局、缓存行为和 I/O。日志、断点、sanitizer、额外的锁或 sleep 都可能让缺陷消失。应将其视为线索，而不是原始行为正确的证明。

使用工具回答具体问题：

| 工具或方法 | 示例问题 |
| --- | --- |
| 调试器、调用栈、核心转储 | 执行在哪里失败，或在哪里不再取得进展？ |
| 内存 sanitizer | 是否正在发生可检测的无效访问或生命周期违规？ |
| 竞态检测器 | 在已运行路径上是否存在可检测的数据竞态？ |
| 性能剖析器 | 在发生性能回归的工作负载下，时间花在了哪里？ |
| 系统跟踪 | 哪项操作阻塞或失败？ |
| 数据包/协议捕获 | 预期事件是否到达相关对等方？ |
| 受控故障注入 | 这种部分失败、延迟、重复或乱序是否产生预测状态？ |

只在任务授权范围内的适当环境中运行有破坏性的实验。保持干预可逆，并与生产变更分开。撤销实验时保留用户编辑。不要仅因为诊断性 sleep、禁用缓存或变异能压制症状，就将它留在最终补丁中。

如果实验不再具备区分力，重新考虑复现用例、观察和模型。在机制仍不明确时，避免大范围重构或随机堆积补丁。

<a id="apply-failure-specific-checks-when-relevant"></a>

## 按相关性进行故障专属检查

| 故障类别 | 关注点 |
| --- | --- |
| 并发 | 哪些操作重叠、共享什么状态、所需顺序、同步、回调/任务生命周期、取消和关闭 |
| 状态机 | 有效/过渡/失败状态、转换决定权、重复或迟到事件、部分转换、冲突标志 |
| 所有权/生命周期 | 创建、借用、缓存/异步引用、清理责任、依赖顺序、部分初始化、重复销毁 |
| 分布式/网络 | 本地、远端、缓存和最终状态；丢失、延迟、重复、乱序、分区、重启、版本或时钟差异 |
| 资源泄漏 | 多次生命周期中的实际资源；区分保留缓存或延迟清理，与不再按要求释放的资源 |
| 性能回归 | 可比的基线、工作负载和环境、延迟分布、吞吐量、利用率和已测量的瓶颈 |
| 崩溃 | 首个无效状态、所有权/生命周期、此前的错误，以及故障是原发还是继发 |
| 挂起/死锁 | 每个被阻塞参与方在等待什么、谁能取得进展，以及等待关系是否形成环 |

对于性能工作，使用测量来区分 CPU/GPU 工作、内存带宽、分配、争用、I/O 和同步。“这段代码看起来开销很大”不是已经确立的性能根因。

对于挂起，在可行时先捕获状态再终止。超时可能是所需行为，但增加超时不能解释意外的循环等待。对于泄漏，内部空指针不能证明底层资源已释放。

<a id="root-cause-gate-and-investigation-outcomes"></a>

## 根因判定关口与调查结果

在把候选解释作为修复依据前，按风险所需程度确立：

- 被违反的契约或不变量。
- 允许无效状态出现的条件或缺陷。
- 将它与观察到的症状连接起来的事件序列。
- 支持证据和已考虑的重要其他解释。
- 拟议改动为何能够中断该机制。
- 重要证据限制，包括复现限制。

对因果主张应用[共享置信程度定义](engineering.md#evidence-and-confidence)。说明具有区分力的证据和仍存在的其他解释；不确定的解释需要进一步调查，或开展明确标为实验的工作，而不是宣称已完成根因修复。

选择明确结果：

| 结果 | 条件 | 下一步 |
| --- | --- | --- |
| 根因已得到充分确立 | 证据以满足下一步行动要求的置信程度支持因果解释 | 交接至编码、设计、契约澄清或外部依赖工作 |
| 调查受阻 / 证据不足 | 缺少某项具体观察、访问能力、环境或决策，阻止了有效推进 | 报告已知事实、缺失前提和下一项有用实验；可能时继续独立工作 |
| 修复已验证 | 实现和所需回归/机制检查已完成 | 按共享指南进行审查并评估任务是否完成 |

只要仍有有用且已获授权的调查可做，就不要用“证据不足”提前退出。当同一个无结论实验无法补足缺失信息时，不要持续重复它。调查受阻不等于故障解决；如果任务还要求实现，完成根因交接也不等于任务完成。

简洁的交接应包含症状与预期行为、复现用例或捕获的证据、因果序列、置信程度与其他解释、受影响的不变量，以及所需修复方向。实现缺陷转入 [coding.md](coding.md)；所有权或架构模型变化转入 [design.md](design.md)。在各自边界上解决不成立的需求、测试或上游假设。

<a id="validate-the-fix-and-neighboring-invariants"></a>

## 验证修复及相邻不变量

同时使用回归证据和机制证据，深度与主张相称：

- **回归证据：**原始故障场景在相关环境中现在满足预期行为。
- **机制证据：**在已声明假设内，改动阻止了调查所识别的因果路径，或对它进行了正确处理。

对于可复现的缺陷，使用 [coding.md](coding.md) 中定义的修复前/后回归检查：未修复版本因目标缺陷失败，已修复版本在可比条件下通过。这是通常应先做的比较；下文的 A/B/A 是在能够解决剩余不确定性时可选的更强干预。如果无法获得可靠比较，说明限制和替代证据，并评估它们是否满足验收基线。

例如，在销毁 registry 前停止并等待 工作线程 退出，可以建立所需的生命周期顺序，前提是关闭协议允许 工作线程 退出。检查无死锁、关闭耗时、取消和错误清理等相邻属性，而不是仅仅把崩溃变成挂起。

一个每 10,000 次运行出现一次的缺陷，不能由 100 次成功运行有力排除。改进复现用例、诱发相关交错执行，或增强机制证据。记录工作负载、运行次数和限制；不要从有限测试宣称缺陷普遍不存在。

可行时，使用隔离的 A/B/A 验证：用原始代码复现，应用候选修复，然后暂时撤回针对因果机制的改动，检查故障是否重现。这能增强改动确有作用的证据，但仍需要因果解释。如果撤回不安全或会干扰用户工作，就不要使用此方法。之后移除诊断性变异，并验证最终版本。

仔细检查 sleep、重试、超时、更大的缓冲区、被忽略的错误和默认值。询问它们处理哪类故障、任何边界为何合理、会留下什么状态，以及更慢或重复执行是否仍可能失败。这些机制可以是合理的契约行为，但不能替代对未知原因的解释。

重新检查相关的相邻不变量：资源清理、同步、延迟、内存、兼容性、错误传播、重试语义和恢复。只有修复影响了这些属性，或仍存在缺口时，才扩大测试范围。

最后简述修复、因果推理、实际针对最终版本执行的检查，以及剩余不确定性。需要审查时，使用 [review.md](review.md)。只有满足任务验收标准时，才报告修复已验证；否则，应将已实现的代码与缺失验证或剩余阻断项区分开。
