# AI Agent 编码指南

<a id="scope-and-minimum-output"></a>

## 适用范围与最低输出要求

遵循 [engineering.md](engineering.md) 中的共享规则。当所需行为和相关架构已得到充分理解时，使用本指南。原因不明的故障转入 [debugging.md](debugging.md)，尚未解决的结构决策转入 [design.md](design.md)。

实施能够建立所需行为并保留受影响不变量的最小完整改动。完整改动可能涉及多个文件；简短的 diff 不自动意味着修复完整。

非平凡工作在修改前，简述预期行为、受影响路径或不变量、计划改动和验证方式。除非计划发生实质变化，否则在各个增量中复用这段说明。完成后报告改了什么、针对最终版本验证了什么，以及任何重要限制。仅在相关时补充架构变化或有意保留的技术债；不要围绕每次修改都输出完整报告。

<a id="establish-the-implementation-contract"></a>

## 确立实现契约

检查受影响的代码、调用者、测试、仓库约定和已接受的设计。明确：

- 哪些条件必须成立，哪些条件必须继续成立。
- 将要改变的端到端路径和可观察影响。
- 已接受的边界：公开行为、所有权、生命周期、状态、并发和依赖。
- 哪些证据能区分正确实现与看似合理但错误的实现。
- 哪些非目标若不明确，可能导致任务范围扩大。

使用共享风险评估选择验证深度。在实现前建立验收场景、所需证据和阻断性缺口，并在编码循环中持续保留。只有明确的契约变化或新证据才能促使重新审视基线，同时记录原因。

定义行为时，不要让它与当前结构产生不必要的绑定。对于资源清理，“关闭后资源不可用，并且可以安全地重新创建”比“调用了 cleanup()”是更有力的行为要求。当内部调用次数本身就是已接受的契约，或属于有针对性的交互检查时，它仍可能有价值；但它不能证明所有外部影响。

只要契约保持不变，私有辅助函数的组织方式、局部算法和内部数据结构通常可以调整。当已接受的架构假设失效时，说明证据和必要的边界变化，然后使用共享架构变更流程。不要为了让实现更容易而悄悄替换所有权模型或公开契约。

<a id="implement-and-validate-coherent-slices"></a>

## 以完整增量实施和验证

优先打通一项端到端行为，而不是先实现所有管理器、工具和基础设施，之后才运行任何路径。例如，先加载一个模型、执行一个请求、返回结果并释放资源。随后按需覆盖无效输入、重复使用或关闭行为。

使用以下循环：

1. 选择一项所需行为，并识别受影响的不变量。
2. 定义预期结果和适当的验证方式。
3. 使用项目现有模式实施最小完整改动。
4. 运行范围最小且相关的构建、分析、测试或运行时检查。
5. 检查 diff，评估新增复杂度、所有权、状态和错误流。
6. 若有具体收益，在范围内简化或重构。
7. **如果验证后代码又发生变化，针对最终版本重新运行受影响的检查。** 如果失败暴露出契约或设计问题，返回负责该问题的阶段。
8. 记录重要证据和缺口；当该增量的结果得到确认时，完成该增量。

不要累积一个庞大却未经验证的子系统。除非后续变化或尚未解决的证据缺口构成理由，否则不要重复已通过的检查。局部措辞或格式修改可能只需要有针对性的人工检查或文档检查。

<a id="choose-evidence-that-tests-the-behavior"></a>

## 选择能够检验行为的证据

使用[共享证据表](engineering.md#evidence-and-confidence)，选择能证明所改行为的最小范围检查。单凭内部标志或调用次数，不能证明外部影响。

从已接受的行为、已知数学结果、协议示例、独立参考数据或其他适当的判定基准推导预期结果。单独的观察者可以验证外部影响，但仍可能共享缓存或错误假设；要检查它实际测量了什么。

避免通过调用被测实现来计算预期值，也不要复制具有相同假设的复杂算法。如果简单数学表达式是从契约独立推导而来，它就是有效的判定基准。独立性关注预期结果的来源，而不是语法是否与实现不同。

对于重要行为，要问：**这个检查能拒绝哪种看似合理但错误的实现？** 有用的思维变异包括跳过清理、不做工作就返回成功、丢弃错误、移除同步、复用过期状态或调用回调两次。只有在能够补充必要证据，并且安全、可逆时，才使用实际的变异或故障注入。

对于可复现的缺陷修复，通常应在未修复和已修复两个版本上运行回归检查：修复前应因目标缺陷而失败，修复后应通过。环境准备错误、缺少符号或无关失败，不能证明测试能检测到该缺陷。保持场景和相关环境可比；必要时使用隔离副本来保留用户工作。如果这种比较不切实际或不可靠，记录原因，并提供替代证据，例如捕获的故障轨迹、受控复现用例或因果时序分析；仅在修复后通过，不能证明该检查对回归的敏感性。

根据受影响行为选择用例：正常输入、有意义的边界、无效输入、部分失败、重复、取消、并发操作、兼容性和恢复，按相关性取舍。不要只优化测试数量或覆盖率百分比。避免只是重述未变化实现细节的低价值测试。

<a id="change-tests-for-a-justified-reason"></a>

## 基于充分理由修改测试

测试失败是需要调查的证据，而不是削弱断言的指令。在改变预期结果前，确定属于哪种情况：

- 已接受契约的证据支持现有预期有误。
- 获授权的行为变更取代了原先正确的预期。
- 行为保持不变，但测试结构或 fixture 必须适应合理的重构。

简述适用的理由，保留对受支持行为的覆盖，并说明修改后的测试为何仍能拒绝重要故障。不要重写需求来迎合补丁。

检查那些移除断言、放宽范围、增加超时、添加重试、跳过不稳定测试、删除失败用例，或通过 mock 移除受影响依赖的改动。这些改动可能合理，但需要行为或环境方面的依据。不要仅为获得绿色 CI，就把预期错误改成成功。

测试可能编码了已接受的可执行规范，也可能编码了错误假设。按共享来源规则评估其权威性，而不是把所有测试一概当作真值或毫无价值。

<a id="keep-ownership-state-and-errors-explicit"></a>

## 明确所有权、状态和错误

如果改动影响访问控制、信任边界、敏感数据、存储数据格式或协议，实施 [design.md](design.md) 中对应的边界和转换决策。验证应包含相关的拒绝/隔离、新旧兼容和转换中断场景。先解决缺失的决策，不要悄悄选择访问或恢复行为；这些检查不授权执行任务范围外的部署或数据迁移。

<a id="ownership-and-lifecycle"></a>

### 所有权与生命周期

当改动影响资源时，检查创建者、所有者、借用者、缓存引用、回调、异步活动和清理责任。即使名义所有者不变，新增的缓存引用或异步引用也可能延长实际生命周期。

对于关闭流程，定义何时停止接收新工作、如何结束正在进行的工作、工作线程 和回调何时停止，以及依赖方与所有者何时失效。检查相关情况，例如部分初始化、重复或并发关闭、工作期间关闭、清理失败和资源重新创建。

必要时，使用运行时证据验证外部清理。内部空指针或 STOPPED 标志不能证明线程已退出、套接字已关闭、共享内存已消失，或远端对等方已不再观察到某项注册。

<a id="state-and-concurrency"></a>

### 状态与并发

保持状态转换的决定权清晰。状态互斥时使用显式状态模型；属性独立时使用独立布尔值。七个标志允许 128 种组合，即使其中只有少数有意义，因此应检查非法组合，而不是自动再加一个标志。

对于每个新增并发元素，定义其所有者、启动/停止行为、取消、共享状态、同步和生命周期依赖。审查锁顺序、队列容量与背压、回调顺序，以及可能在所有者失效后仍持续的工作。即使只需几行代码，增加后台 工作线程 也可能改变架构。

<a id="error-flow-and-fallback"></a>

### 错误流与回退

从起点到调用者追踪重要错误。识别清理责任、部分状态、恢复策略，以及重试是否有界且安全。查找被吞掉的错误、丢失的上下文、部分失败后仍报告成功、只记录却未按需传播错误，以及传播错误却没有清理的情况。

添加回退前，先对失败分类：不受支持的输入、预期的外部失败、暂时性运行故障、资源故障、内部不变量被破坏或编程缺陷。GPU 不可用后降级到 CPU 执行，只有在该行为受到支持时才有效。为不可能出现的内部状态返回默认对象，可能会掩盖缺陷。

超时、重试或回退需要具体的失败类别和明确的结果。它不能掩盖原因不明的竞态，也不能把失败伪装成成功。

<a id="control-complexity-and-refactoring"></a>

## 控制复杂度与重构

评估该增量引入的重要复杂度：状态、标志、分支、抽象、依赖、所有权路径、锁、线程、队列、回调、重试和配置。记录显著新增项及其理由；不要在面向用户的输出中逐一列举每个普通条件判断。

优先保持状态决定权、所有权责任以及各项不变量的局部解释清晰。避免把同一条规则散落在无关标志、回调和辅助函数中。

反复出现的特例是在提醒重新审视模型。同一子系统出现第三个实质性例外是有用的警报，不是自动要求重设计的数字规则。应检查契约、状态表示或责任边界是否有误。

当重构能在任务范围内降低推理成本、重复或歧义时，才进行重构。不要仅为了缩短函数、拆分文件、添加接口或应用某种模式而重构。可行时，将大型重构与行为变更分开，以便继续诊断回归。说明要保留的行为，并在重构后重新验证。

检查最终 diff 中是否有无关格式调整、顺手重命名、推测性的兼容分支、不必要的包装层、重复机制，以及声称了代码尚未建立的保证的注释。只移除自己附带引入的无关修改；保留用户已有编辑。将无关问题记录为后续事项。

<a id="keep-performance-evidence-concrete"></a>

## 让性能证据具体可查

在受影响的关键路径上，检查复制、分配、序列化、锁、阻塞 I/O、上下文切换、设备同步和传输。识别重要开销，但不自动优化它们。

使用测量结果、硬性要求、已知硬件约束或有力的结构证据来证明新增复杂度合理。对延迟、吞吐量或内存使用改善的实际主张，需要可比的测量结果。记录工作负载、环境和有意义的波动，而不是依赖一次有利的运行。

不要为假想瓶颈增加自定义分配器、无锁队列、缓存、批处理、零拷贝基础设施或异步流水线。当高开销行为与已确立要求冲突时，避免无必要地将它固化进稳定 API。

对于已接受的重要限制，记录原因和升级触发条件。例如：启动期间同步加载模型可以接受；当热加载成为受支持的要求时再重新评估。将来可能的优化，不意味着今天就需要一个新子系统。

<a id="completion-and-review-handoff"></a>

## 完成与审查交接

使用[共享完成规则](engineering.md#persistent-records-and-completion)，将最终版本的行为和证据与验收基线对齐。检查最终 diff；报告行为变化、实际验证和重要缺口，不重复完整检查清单。

遵循[独立审查规则](engineering.md#independent-review-policy)。用户请求或规则要求审查时，读取 [review.md](review.md)。交接受影响契约、补丁、验证证据和已知限制；将作者的信心与独立检查的证据分开。
