# 编码实现

**简体中文** · [English](en/coding.md) · [文档首页](../README.zh-CN.md#指南导航)

<a id="scope-and-minimum-output"></a>

## 适用范围与最低输出要求

遵循 [engineering.md](engineering.md)。行为和架构明确时使用；原因未知的故障转 [debugging.md](debugging.md)，未决结构选择转 [design.md](design.md)。实现保持不变量的最小完整改动；小 diff 不代表修复完整。

非平凡修改前简述预期行为、路径／不变量、改动和验证；计划不变时复用。完成时报告改动、最终版本验证和重要限制。

<a id="establish-the-implementation-contract"></a>

## 确立实现契约

检查代码、调用者、测试、项目约定和已接受设计，明确必须改变／保持的条件、端到端路径与外部效果、行为及所有权／生命周期／状态／并发／依赖边界、可排除错误实现的证据和非目标。

按[共享风险与证据规则](engineering.md#evidence-and-confidence)在实现前建立验收场景、证据和阻塞缺口；只因契约变化或新证据调整并记录理由。行为要求独立于内部结构；内部调用可证明已接受契约或针对性交互，但不能证明全部外部效果。契约不变时可调整私有实现；架构假设失效时按[共享架构变更流程](engineering.md#scope-and-architecture-changes)处理，不得暗改公共契约或所有权模型。

<a id="implement-and-validate-coherent-slices"></a>

## 以完整增量实施和验证

每次打通一项端到端行为：确定行为与不变量，定义结果和验证，沿用项目模式做最小完整改动，运行最小相关检查，检查 diff 及复杂度、所有权、状态和错误流，并仅在有具体收益时范围内简化。失败暴露契约或设计问题时返回对应阶段。

**验证后代码又变化时，必须针对最终版本重跑受影响检查。** 不积累庞大未验证子系统；除后续变化或证据缺口外不重复已通过检查。局部文字或格式修改可只做针对性人工或文档检查。

<a id="choose-evidence-that-tests-the-behavior"></a>

## 选择能够检验行为的证据

按[共享证据规则](engineering.md#evidence-and-confidence)选择最小检查。预期结果应来自契约、已知数学结果、协议示例或独立参考数据；不得由被测实现生成或复制其假设。检查应能拒绝合理但错误的实现；内部标志、调用次数或共享缓存的观察者不能单独证明外部效果。

可复现缺陷通常须做可比的修复前失败／修复后通过；环境、符号或无关失败不证明敏感性。无法可靠比较时说明原因，并提供故障轨迹、受控复现或因果时序。按相关性选择正常、边界、无效、部分失败、重复、取消、并发、兼容和恢复场景；数量或覆盖率不能替代行为证据。实际变异或故障注入仅在必要、安全、可逆时使用。

<a id="change-tests-for-a-justified-reason"></a>

## 基于充分理由修改测试

失败测试是调查证据，不是放宽断言的指令。修改预期必须有以下理由之一：已接受契约证明旧预期错误；获授权行为变更取代旧契约；行为不变而测试结构或 fixture 适应合理重构。说明理由，保留仍受支持行为，并确保修改后仍能拒绝重要故障。

删除断言／失败用例、放宽范围、增加超时／重试、跳过测试或 mock 掉受影响依赖都须有行为或环境依据，不能只为绿色 CI。按[共享来源规则](engineering.md#intended-behavior-and-source-authority)判断测试权威性。

<a id="keep-ownership-state-and-errors-explicit"></a>

## 明确所有权、状态和错误

访问控制、信任边界、敏感数据、存储格式或协议变化须落实 [design.md](design.md) 的边界和转换决定，并验证相关拒绝／隔离、新旧兼容、中断与恢复。缺失决定先解决；这些检查不授权范围外部署或迁移。

<a id="ownership-and-lifecycle"></a>

### 所有权与生命周期

资源变化须检查创建者、所有者、借用者、缓存／异步引用、回调和清理。关闭流程明确停止接收、结束在途工作、线程／回调停止和依赖失效顺序，并按需检查部分初始化、并发关闭、工作中关闭、失败和重建。外部清理须在必要时用运行观察证明；空指针或 `STOPPED` 不能证明线程、套接字、共享内存或远端注册结束。

<a id="state-and-concurrency"></a>

### 状态与并发

明确状态转换权；互斥状态用显式模型，独立属性才用独立布尔值，并检查非法组合。每个新增并发元素须定义所有者、启动／停止、取消、共享状态、同步和生命周期依赖，并检查锁顺序、队列容量／背压、回调顺序及所有者失效后的工作；少量代码也可能造成架构变化。

<a id="error-flow-and-fallback"></a>

### 错误流与回退

从起点到调用者追踪重要错误，明确清理、部分状态、恢复及重试的边界和安全性。检查吞错、丢上下文、部分失败后报成功、只记录不传播或传播不清理。回退前区分不支持输入、预期外部失败、暂时运行故障、资源故障、内部不变量破坏和编程缺陷。超时、重试或回退必须对应具体故障类别和明确结果，不能掩盖未知竞态或把失败伪装成成功。

<a id="control-complexity-and-refactoring"></a>

## 控制复杂度与重构

评估新增状态、抽象、依赖、所有权、并发、重试和配置，并说明显著复杂度的理由。反复特例提示检查契约、状态或责任边界；第三个实质例外只是警报，不自动要求重设计。

只为范围内降低推理成本、重复或歧义而重构；大型重构尽量与行为变化分开并重验行为。最终 diff 去除自己引入的无关格式、重命名、推测分支、多余包装／机制及超出代码保证的注释；保留用户编辑，无关问题只记录。

<a id="keep-performance-evidence-concrete"></a>

## 让性能证据具体可查

按需检查关键路径的复制、分配、序列化、锁、阻塞 I/O、设备同步和传输，不自动优化。新增复杂度须有测量、硬性要求、硬件约束或有力结构证据；性能改善须有记录负载、环境和波动的可比测量。不得为假想瓶颈增加定制分配器、无锁队列、缓存、批处理、零拷贝或异步流水线。保留的重要限制记录理由和升级触发条件。

<a id="completion-and-review-handoff"></a>

## 完成与审查交接

按[共享完成规则](engineering.md#persistent-records-and-completion)将最终行为和证据逐项对齐验收基线。检查最终 diff，报告行为、实际验证与重要缺口。按[独立审查规则](engineering.md#independent-review-policy)判断要求；需要审查时读取 [review.md](review.md)，交接受影响契约、补丁、证据和限制，并区分作者信心与独立证据。
