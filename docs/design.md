# 架构设计

**简体中文** · [English](en/design.md) · [文档首页](../README.zh-CN.md#指南导航)

明确行为、边界和取舍，再实现。

<a id="scope-and-minimum-output"></a>

## 适用范围与最低输出要求

遵循 [engineering.md](engineering.md)。本指南用于结构变更、难撤销决定和有重要取舍的行为变更；局部实现调整无需完整流程。

设计当前需求所需的最小系统，只为有依据的未来变化保留边界。简短设计至少写明：

- 问题、结果、非目标；
- 约束、假设、所选方案；
- 受影响契约、关键不变量；
- 现实替代方案、取舍、未决项；
- 证明结果所需的验证。

新子系统或广泛结构变更再补充相关组件、数据流、所有权、故障和性能视图；省略不适用项，不编造未来场景。

<a id="establish-priorities-and-requirements"></a>

## 明确优先级与需求

先明确使用者、问题、输入输出、项目阶段和可观察成功判据。优先级影响决定时，从已接受目标和约束得出并显式说明，不能默默编造。

| 分组 | 动作 |
| --- | --- |
| 现在实现 | 打通当前结果及端到端验证 |
| 现在保留边界 | 只为具体且很可能发生、否则代价高的变化建立最小边界 |
| 完全推迟 | 不为低可信或遥远可能性增加复杂度 |

非目标可能扩大范围时明确列出。

<a id="identify-constraints-and-reversibility"></a>

## 识别约束与可逆性

先检查现有决定和模式，包括所有权、错误、API、资源、线程、配置与测试。区分已知约束、待验证假设和未来可能性；覆盖相关行为、性能、环境、可靠性和交付限制。

按消费者和持久化影响判断撤销成本。公共 API、所有权/生命周期、并发模型、进程边界、持久数据 schema、协议格式和外部数据表示通常难撤销；小配置或 CLI 参数若已有外部依赖，也属于兼容边界。

<a id="resolve-feasibility-with-bounded-experiments"></a>

## 用有界实验验证可行性

设计依赖未证实行为时，先做隔离、可逆的小实验。写明问题、假设、环境、最小实验、判定证据和停止条件；遵守已有资源预算和授权，不改公共契约、生产状态或依赖。

结论标为“支持 / 否决 / 尚无定论”，说明设计影响。实验只证明其条件下的属性；无定论时给出下一项有区分力的步骤。实验代码需经正常编码、验证和审查后才能交付。

<a id="build-the-minimal-architecture"></a>

## 构建最小架构

先给出一条完整价值路径：输入、验证、执行、结果、资源释放。优先少量组件、直接数据流、清晰依赖、明确所有权和小型公共契约。

每个抽象必须隔离具体变化、所有权、生命周期、故障、性能、外部依赖或测试边界。模式只在解决真实问题时使用；偏离仓库模式需有具体理由，不能暗中引入第二套框架。

<a id="describe-affected-boundaries"></a>

## 描述受影响边界

结构工作只使用能揭示实际风险的视图，小型设计可合并为文字或一张图。

<a id="components-and-data-flow"></a>

### 组件与数据流

展示依赖和重要端到端路径，标出验证、转换、序列化、复制、所有权转移、上下文切换及外部效果。稳定边界需定义输入、输出、前置条件、错误、版本和兼容预期。

<a id="ownership-and-lifecycle"></a>

### 所有权与生命周期

说明重要资源的创建、拥有、借用、转移和销毁者，以及异步引用和缓存句柄。定义资源失效前必须停止的活动和关闭顺序；按需覆盖取消、部分初始化、重复关闭、清理失败和重建。组件图不能证明生命周期安全。

<a id="state-concurrency-and-errors"></a>

### 状态、并发与错误

定义有效状态与转换、修改权、重复/迟到事件、任务与线程的启动停止取消、共享状态与锁序、回调生命周期、队列容量/背压/关闭、错误与清理责任，以及重试是否有界且安全。

检查部分初始化、依赖消失、关闭期回调、部分成功后超时。只实现契约要求的恢复；不要用后备行为掩盖编程错误。并发必须由具体需求支持。

<a id="trust-boundaries-and-sensitive-data"></a>

### 信任边界与敏感数据

涉及不可信输入、身份/授权或敏感数据时，标出参与者、受保护对象和信任变化点；定义输入校验、身份、授权及用户/租户隔离。追踪数据经输出、错误、日志、缓存和外部调用的路径，并在真实执行限制的边界验证允许/拒绝场景。外部输入本身不要求新增身份认证；只做相关的最低安全检查。

<a id="persistent-data-and-protocol-transitions"></a>

### 持久数据与协议转换

改变持久表示、配置兼容或协议时，列出既有状态和受支持参与方；定义升级顺序、混合版本期、转换/回填、中断、重入和恢复。应用回退不代表数据可恢复。

用隔离环境验证受支持的新旧状态与中断转换。执行前明确不可逆步骤；部署不在范围时只交接要求和实现证据，不声称已迁移或发布。

<a id="evaluate-performance-and-reliability"></a>

## 评估性能与可靠性

优化前明确负载、指标、环境、关键路径和测量方法；区分估算与实测。检查复制、分配、阻塞、序列化、竞争、上下文切换和设备同步，实际改进必须有可比较测量。

无具体需要时不引入无锁、自定义分配、缓存、批处理、零拷贝或分布式执行。用明确故障场景评估安全完成、明确失败、回滚、清理或恢复，并定义可区分结果的运行观察。

<a id="test-likely-changes-and-simplify"></a>

## 检验可能的变更并简化

只选择少量有依据的未来场景，通常不超过三至五个；没有依据时为零。检查它们是否迫使公共 API、所有权、状态、数据表示或并发大改，必要时只保留小边界。

定稿前删除无责任的层、无依据的接口/插件机制/动态配置和无测量支持的优化。比较现实替代方案，尽可能包含更简单方案。此检查不授权清理无关代码。

<a id="record-decisions-challenge-and-hand-off"></a>

## 记录决定、质疑与交接

复用现有设计记录或 ADR，记录重要决定、限制、理由和具体重审触发条件。按[独立审查规则](engineering.md#independent-review-policy)质疑无依据假设、所有权、难撤销边界、瓶颈、部分失败和复杂度；设计审查不能替代最终实现审查。

行为、范围、硬约束、结构、不变量和验证策略足够清楚，且无事项阻止安全推进时进入实现。向 [coding.md](coding.md) 交接接受的决定、契约、假设、限制和验证预期；新证据推翻假设时返回设计。
