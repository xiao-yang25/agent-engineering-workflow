# AI Agent 架构与设计指南

<a id="scope-and-minimum-output"></a>

## 适用范围与最低输出要求

遵循 [engineering.md](engineering.md) 中的共享规则。本指南适用于结构变更、撤销成本高的决定，以及涉及重要设计取舍的行为变更。局部实现调整不要求完整的设计流程。

设计满足当前需求的最小系统，同时保留有充分依据的未来变更所需的必要边界。按照项目的实际优先级，平衡交付速度、简单性、可靠性、性能和可维护性。

对于范围集中的决定，一份简短说明即可：

- 问题、所需结果和非目标。
- 相关约束与假设。
- 所选方案、受影响契约和关键不变量。
- 重要替代方案、取舍和未决事项。
- 将结果视为已得到证实之前所需的验证。

使用共享风险评估和验收基线，决定每个边界需要多少证据。结构变更本身不能决定验证强度。

对于新子系统或广泛的结构变更，补充下文所述的相关组件、数据流、所有权、失败和性能视图。省略不适用章节，复用已接受的设计资料。不要为了填满模板而编造未来场景或被否决的替代方案。

<a id="establish-priorities-and-requirements"></a>

## 明确优先级与需求

在划分模块或选择模式前，明确谁使用系统、需要解决什么问题、主要输入和输出、项目当前阶段，以及可观察的成功判据。

优先级对决定有实质影响时，应明确说明。早期产品可能在满足正确性和硬约束后优先考虑交付速度；机器人控制路径可能优先考虑确定性延迟和生命周期安全。从已接受的目标和约束推导优先级，解决重要歧义，而不是默默编造优先级。

将需求分为三组：

| 分组 | 判据 | 设计动作 |
|---|---|---|
| 现在实现 | 当前结果所必需 | 包含端到端实现和验证路径 |
| 现在保留边界 | 某项具体且很可能发生的未来变更，否则将需要高昂的支持成本 | 只引入有依据的最小边界；推迟功能实现 |
| 完全推迟 | 可信度低或遥远的可能性 | 仅在有用时记录；不增加当前复杂度 |

例如，若已接受的近期路线图中包含另一个推理后端，一个小的运行时边界可以隔离后端专属行为。这不足以证明插件注册表、动态加载器或多个未使用后端是必要的。没有可信的变化需求时，直接使用当前后端可能已经足够。

非目标可能导致任务范围扩大时，应明确列出。推迟的能力可以留待未来考虑，不必现在实现。

<a id="identify-constraints-and-reversibility"></a>

## 识别约束与可逆性

提出新结构前，检查仓库现有模式和已接受的决定。查找所有权约定、错误模型、API 形态、资源管理、线程使用、配置和测试实践。

区分已知约束、待验证假设和未来可能性。相关约束可能包括：

| 领域 | 问题 |
|---|---|
| 行为 | 需要哪些输入、输出、兼容性和部署模式？ |
| 性能 | 适用哪些延迟、吞吐量、抖动、启动、内存或资源限制？ |
| 环境 | 支持哪些操作系统、语言、硬件、编译器、框架版本和部署平台？ |
| 可靠性 | 需要怎样的失败、清理、重启、恢复或可用性行为？ |
| 交付 | 可以接受怎样的期限、工程投入和运行复杂度？ |

设计投入应与撤销成本相称。私有名称、辅助函数和局部组织通常容易修改；公共 API、所有权与生命周期契约、并发模型、进程边界、持久化数据模式（schema）、协议传输格式和供外部消费的数据表示通常不是如此。

通过消费者和持久化影响判断可逆性，而不是通过大小或语法判断。脚本、用户、存储数据或部署依赖 CLI 参数和小型配置格式时，它们就成为兼容边界。内部细节如果存在广泛耦合，修改成本也可能很高。

<a id="resolve-feasibility-with-bounded-experiments"></a>

## 用有界实验验证可行性

如果设计选择依赖现有证据无法证实的行为，在确定架构前先做小实验。例如检查依赖的取消行为，或衡量拟议数据路径是否满足资源预算。这不要求已经有完整设计，也不要求已经存在缺陷。

说明问题、待验证假设、最小实验、相关环境、选择或否决方案所需的证据，以及停止规则。将投入限定在该决定上，并遵守已给出的时间或资源预算。保持实验隔离且可逆；不得超出现有授权修改公共契约、生产状态或依赖。

以“支持”“否决”或“尚无定论”给出结论，并说明对设计的影响。成功的微基准测试或模拟只能证实其条件下被测试的属性。尚无定论时，指出下一个有区分力的步骤或缺失前提，而不是无限扩展原型。实验代码只有在明确决定实施，并完成正常的编码、验证和审查检查后，才能成为交付内容；不能因为实验成功就自动接受它。

<a id="build-the-minimal-architecture"></a>

## 构建最小架构

先展示一条能够交付当前价值的完整路径，例如：

```text
输入 → 验证 → 执行 → 结果 → 资源释放
```

优先选择少量组件、直接的数据流、清晰的依赖方向、明确的所有权和小型公共契约。一个完整一致的设计可以跨多个文件；目标不是让文件数最少。

每个抽象都应隔离一项具体关注点，例如独立变化、所有权、生命周期、故障隔离、性能、外部依赖或有意义的测试切入点。检查它隐藏了什么复杂度，或保证了什么不变量。只有一个实现并不自动意味着接口没有必要，多个类也不自动意味着需要框架。

只有模式能解决问题时才使用它。正确性和硬约束决定方案；在这些约束内，以仓库一致性和简单性指导选择。具体理由可以支持偏离现有模式，但应记录其影响，而不是默默引入第二套框架。

<a id="describe-affected-boundaries"></a>

## 描述受影响边界

对于实质性结构工作，使用能揭示实际风险的视图。小型设计可以将这些内容合并为文字或一张图。

<a id="components-and-data-flow"></a>

### 组件与数据流

展示谁依赖谁，并追踪重要的端到端路径。在相关时识别验证、转换、序列化、复制、所有权转移、上下文切换和外部可见效果。

定义稳定边界上的契约：输入、输出、前置条件、错误、支持版本和兼容预期。不要让正确性依赖组件之间未定义的行为。

<a id="ownership-and-lifecycle"></a>

### 所有权与生命周期

对于重要资源，明确谁创建、拥有、借用、转移和销毁它们。包括异步引用和缓存句柄。定义在资源失效前，哪些依赖它的活动必须停止。

关闭顺序可以是：

```text
拒绝新工作 → 按策略处理活动中的工作
→ 停止并等待工作线程退出 → 释放依赖资源 → 销毁所有者
```

实际顺序必须遵循系统的依赖关系。当取消、部分初始化清理、重复关闭、清理失败和重新创建属于受支持行为时，应说明这些行为。仅有组件图不能证实生命周期安全。

<a id="state-concurrency-and-errors"></a>

### 状态、并发与错误

涉及状态或并发时，定义：

- 有效状态与转换，包括部分失败和恢复。
- 状态修改权的归属，以及重复或迟到事件的处理。
- 谁拥有、启动、停止和取消每个任务或线程。
- 共享状态、同步、锁顺序和回调生命周期。
- 队列语义、容量、背压和关闭行为。
- 错误流向、谁负责清理，以及重试是否有界且安全。

检查初始化中途失败、依赖消失、关闭期间回调到达，或操作部分成功后超时时会发生什么。仅在契约要求时才要求恢复；不要把编程错误变成看似成功的后备行为。

并发必须满足具体需求。不要仅因为默认采用某种架构风格就增加线程或异步执行。

<a id="trust-boundaries-and-sensitive-data"></a>

### 信任边界与敏感数据

当变更接受不可信输入、改变身份或授权，或处理敏感数据时，识别参与者、受保护操作或数据，以及信任发生变化的位置。定义输入验证，以及契约要求的身份、授权或用户／租户隔离。识别有意公开的操作；不要仅因输入来自外部就引入身份认证。在相关时追踪受保护数据经过输出、错误、日志、缓存和外部调用的路径。

将相关的输入接受／拒绝场景，以及适用访问限制时的允许／拒绝操作，纳入验收基线。检查实际执行限制的边界：仅有客户端控制或正常路径测试，不能证实预期访问限制。即使没有单独安全指南，也应执行这些最低检查；不要对无关变更要求完整威胁模型。

<a id="persistent-data-and-protocol-transitions"></a>

### 持久数据与协议转换

当变更改变存储数据的表示或解释、持久化配置的兼容性，或某个协议时，识别既有状态，以及受支持的读写方或对端。定义支持的升级顺序、任何必要的混合版本运行期、转换或回填行为，以及转换中断或中途重复执行时会发生什么。契约不变时的普通读写需要相关正确性和失败检查，不需要迁移计划。

说明如何发现未完成的转换，以及如何通过回滚、还原或向前修复来恢复。不要假定回退应用代码就能恢复已改变的数据。使用适当测试夹具或隔离环境，验证受支持的新旧状态和有代表性的中断转换。执行前说明不可逆步骤和所需决定。如果部署不在任务范围内，交接这些要求并报告实现验证情况，不得声称已发生迁移或发布上线。

<a id="evaluate-performance-and-reliability"></a>

## 评估性能与可靠性

选择优化前，先明确性能要求。识别负载、目标指标、环境、关键路径和测量方法。区分估算预算与测量结果。

例如，可以将端到端延迟目标分配为请求处理、预处理、数据传输、执行和后处理的预算。在预期负载下验证总结果；预算表不能证明已经达到目标。

检查可能占主导的成本：复制、分配、阻塞操作、序列化、竞争、上下文切换和设备同步。以测量、已知硬件约束或有力的结构证据支持设计选择。声称实际改进必须有测量依据。

没有具体需要时，避免无锁结构、自定义分配器、缓存、批处理、零拷贝机制或分布式执行。同时，如果可信需求需要另一种内存或执行模型，就不要无必要地将高成本表示固定进稳定 API。

通过明确的失败场景与结果评估可靠性：按策略安全完成、明确失败、回滚、清理或恢复。识别运行时必须观察哪些信息，才能区分这些结果。

<a id="test-likely-changes-and-simplify"></a>

## 检验可能的变更并简化

如果为未来做准备有依据，选择少量具体场景，通常不超过三到五个。没有得到支持的未来需求时，零个也合适。

对于每个场景，识别受影响模块，以及公共 API、所有权、状态、数据表示或并发是否必须变化。若很可能发生的场景会迫使系统大幅重写，考虑现在保留一个小边界。若遥远场景代价高，不要自动为它做准备。

定稿前，进行与设计规模相称的简化检查：

- 服务能否改为局部模块，工厂能否改为直接构造？
- 某一层是否执行策略、管理所有权、转换或隔离，还是仅仅转发调用？
- 拟议接口是否隔离了真实关注点？
- 插件机制、分布式协调、通用 DAG 执行或动态配置是否确实需要？
- 每项优化背后是否有证据或硬约束？

从方案中删除没有依据的复杂度。这是对本任务设计的审查，不是无关仓库清理的授权。

对于重要决定，将所选方案与现实的替代方案比较；可行时包括更简单的方案。解释实际取舍，而不是列出从未成为候选的复杂模式。

<a id="record-decisions-challenge-and-hand-off"></a>

## 记录决定、质疑与交接

按照共享指南，为重要决定复用已有设计记录或 ADR。记录有意保留的限制、理由和具体重审触发条件。例如，对不频繁的注册表更新使用互斥锁可能可以接受，直到性能分析显示存在竞争，或并发加载成为受支持需求。

遵循[共享独立审查规则](engineering.md#independent-review-policy)；当尽早质疑可以解决重要设计不确定性时，应寻求这种质疑。关注缺乏支持的假设、不清晰的所有权、撤销成本高、不可避免的瓶颈、部分失败和不必要的复杂度。重新设计方案前，先评估发现。设计审查评估就绪程度，不能替代最终实现所需的任何审查。

当行为、范围、硬约束、所选结构、相关不变量和验证策略已足够清晰，且没有未决事项阻止安全推进时，设计就可以进入实现。未来实现细节和非阻塞问题可以保持未决。

将已接受的决定、受影响契约、重要假设、限制和验证预期交给 [coding.md](coding.md)。实现或运行时证据推翻某个假设时，重新审视设计；不要将文档视为永久正确。
