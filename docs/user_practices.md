# 使用 AI 工作的人：实践指南

**简体中文** · [English](en/user_practices.md) · [文档首页](../README.zh-CN.md#指南导航)

面向使用 Agent 完成工程任务的人，关注任务定义、上下文、授权、执行、纠偏、验收和经验复用。按任务选用建议；简单任务直接说明需求即可。工程职责、授权和验收沿用现有指南，本文不新增强制流程。

## 人的工作习惯

1. **先选值得解决的问题。** 说明结果服务谁、下一项决定是什么、怎样判断完成。生成成本降低后仍需安排优先级；没有实际用途的产物可以不做。
2. **区分交付、学习和探索。** 熟悉且可验收的任务可委派较完整的增量；学习陌生机制时请求解释、例子与反馈，并自己复述或完成小练习；探索任务要求候选方案、证据、未知和下一步实验。一个任务可兼有多个目标，按需要说明。
3. **给可用背景，留下执行空间。** 提供关键文件、约束、版本、好坏示例和优先取舍。稳定信息引用现有入口，单次例外在当前任务更新；按缺口补材料，不要求一次写出完美提示。
4. **让委派范围匹配验收能力。** 能判断结果时委派完整、可验收的成果；陌生或难验证的工作先确定核验办法或取得适当审查。人的用途判断、业务取舍与授权同 Root 的工程判断及最终验收配合，具体职责见现有协作指南。
5. **主动核对关键结论。** 对重要决定询问成立条件、反例及会改变结论的证据，再查原始来源或实际状态。多次模型回答一致仍需证据；纠偏时指出具体遗漏，并说明原目标是否仍有效。
6. **按注意力安排并行。** 先完成一个可验收增量，再按任务独立性与自己的审阅能力增加并行。保留稳定目标，及时处理必要决定；已有授权范围内的执行由 Agent 持续推进，具体限制见协作指南。
7. **以实际结果积累经验。** 验收时体验真实使用路径。回看哪些决定需要自己参与、哪些步骤可继续委派、哪些返工来自目标或材料缺口；把可复用案例与证据索引放回原记录。比较质量、实际耗时、人工纠偏和返工，数据不够时保留未知。

“已覆盖”指指南已有约定，不代表每个真实任务都执行到位。

| 人的关注点 | 已有工作流入口 | 使用者可补充的动作 |

| 目标、取舍、完成标准 | [流程深度](engineering.md#select-process-depth)、[验收证据](engineering.md#evidence-and-confidence) | 说明用途及本次交付/学习/探索目标；简单任务不强制填表 |

| 委派与审阅能力 | [Agent 协作](agent_selection.md) | 用可判断的成果安排工作；按可及时验收的数量增加并行，不擅自扩大执行者授权 |
| 来源核验与反例 | [来源权威](engineering.md#intended-behavior-and-source-authority)、[独立审查](engineering.md#independent-review-policy) | 在重要取舍处核查假设；讨论反例不替代必需独立审查 |
| 人的理解与结果表达 | [表达与交付](engineering.md#expression-and-delivery) | 请求能帮助理解的解释、图或交互；自己检验能否解释关键机制 |

优先试用三个动作：开始时说明本次主要目标；重要决定核验关键事实或反例；交付后回看一次实际返工原因。按任务需要使用，不增加固定次数的确认、复述或复盘门禁；没有新证据时不追加规则。

## 一次任务怎样配合

新项目的启动讨论按需要明确目标/非目标、硬约束、关键方案与选型、阶段结果、验收和可用材料。区分已决定事项、待验证假设和可自主处理的细节；未知可行性先做有界实验，不要求讨论完所有实施细节才开始。设计与项目接入方法复用现有指南。

- **开始：** 说明用途、所需结果、关键材料、验收与允许范围；复杂或陌生任务补充取舍和学习目标。
- **进行：** 让 Agent 推进已有授权工作；在缺必要决定时回应，在具体偏差出现时纠正，明确变化是补充还是替换原目标。
- **交付：** 看实际产物、关键验证和未验证项，按真实用途体验结果；Agent 仍负责应做的验证，使用者无需重复全部检查。
- **接续：** 保留重要决定、未完成事项与证据入口；重复问题按现有工作流改进机制处理。

## 提问与补充信息

不必先写出完整需求书。Agent 应先定位已有材料，再按[澄清原则](engineering.md#clarifying-the-task-with-the-user)帮助补齐影响下一步的信息。下面是可选提示，不是每次都要回答的清单。

| 方面 | 可以补充的信息或提出的问题 |
| --- | --- |
| 用途与边界 | 谁在什么场景使用？首个结果是什么？本次明确不做什么？ |
| 约束与取舍 | 必须兼容什么？时间、成本或维护性中优先哪项？哪些选择由你推荐并解释？ |
| 材料与例子 | 哪些文件是依据？有没有喜欢的结果、不可接受的反例或现有失败？ |
| 验收与范围 | 我能怎样体验或核验？允许修改和执行到哪里？哪些事项需要我决定？ |
| 理解与接续 | 用什么形式解释最合适？哪些是假设？下一阶段需要保留哪些决定与证据？ |

可以直接这样发起或纠偏：

- **开始：** “首版给我自己使用，先完成一个可体验的完整场景。参考现有材料，请指出真正缺失的决定并推荐选项；其余细节在允许范围内自主推进。”
- **取舍：** “列出两种现实方案，推荐一种，说明代价和什么证据会改变你的推荐。”
- **理解：** “我没理解这里的重试机制。先给一个数值例子；如果交互能帮助理解，再做可调参数的解释。”
- **纠偏：** “这个结果漏了断网场景，原目标继续有效。请补边界验证，并说明哪些结论需要修改。”

## 用具体结果帮助讨论

- 目标尚模糊时，先看最小草图或可体验的小样，再收窄需求；这是获取反馈的方法，不自动批准全部实施或发布。
- 用好例子和反例明确质量差异，说明差异来自内容、行为还是呈现；不要让 Agent 只猜“更专业”“更好看”的含义。
- 在重要选择处看简短取舍摘要；在重复纠偏无进展时，请 Agent 对比竞争假设并提出下一项有区分力的实验，复用现有设计和调试方法。
- 交付时要求实际使用入口、关键验证与限制；解释产物按[制作指南](explanation_artifacts.md)选择，不能代替实际产品验收。

## 复用成功实例

以已验证产物为核心，附上复用所需的材料、关键决定、纠偏、验收证据、版本和适用边界；原始过程只保留位置索引，不复制整段对话。产物通过验收不证明协作方法高效，一次成功也不证明稳定收益。产物与做法由原项目或原任务维护；用于比较工作流改动的回归样例只在既有私有索引登记，按[回归规则](workflow_evolution.md#小型真实任务回归集)核验，不另建案例库。

## 工作流用什么形式承载

| 内容 | 合适的载体 | 增加机制的依据 |
| --- | --- | --- |
| 人的使用方法与取舍 | README 与本文 | 按需阅读，面向人的理解 |
| 工程约束和方法 | 简短入口与专项指南 | 入口导航、正文按需加载；同一规则一个维护位置 |
| 稳定且可判定的重复动作 | 现有脚本、测试或 CI | 有真实重复或遗漏证据时自动化，实际执行验证 |
| 进度、决定和运行证据 | 原任务记录及允许的私有索引 | 能定位当前状态、版本与未决项 |
| 稳定、可复用且需要判断的多步骤过程 | 可选 Skill | 按 [沉淀规则](project_workflow.md#重复动作的沉淀与告知)评估，显式请求后创建或启用 |

当前形态可保持为“文档入口 + 可执行检查 + 任务证据”。文档适合表达与审阅原则，实际权限由宿主执行，检查由真实运行证明；只有当前载体出现具体缺口时再评估平台或额外工具。本文不改变模型、授权、调度或业务项目配置。
